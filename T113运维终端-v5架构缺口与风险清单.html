0. 总体结论

架构骨架可用，细节完备度不足。 v5 相对 v4 是"提纯"而非"整合"：新增了工程治理章节（H2 标题 14 → 20 个），同时删掉了功能实现级细节（文档量 952 → 723 行）。

维度评分（0~5）说明
进程与并发模型5单 Reactor + 2 有界 worker + 健康线程，业务路径无锁
状态与数据所有权5一库一写者，Web 不直连业务库
可测试性5fuzz + 故障注入 + 72h 长稳 + 10 条验收场景
网络与双 WAN4已修正 v4 的"只改路由不重连"错误；缺计费保护策略
进程通信 IPC4SEQPACKET + 版本化头 + SO_PEERCRED；缺大数据路径
OTA 与回滚4应用/系统双路径已拆开；缺提权触发机制
安全边界4强制签名 + 服务白名单；提权路径有缺口
媒体与存储3上限全是符号无数字

v5 已修正 v4 的两处硬错（值得保留）

  1. 双 WAN：v4 §5.3"切换 = netlink 改路由（毫秒级），不是应用重连"是错的。v5 §7.2 明确 "普通 TCP 不能跨接口迁移，'只改路由不重连'不作为实现方案"，切换事务含关闭旧接口 TCP + 新出口重建。
  2. OTA：v4 把"应用 A/B"与"系统 U-Boot A/B"混为一谈；v5 §11.2/§11.3 拆成两条独立路径。

2. P0 缺口详情

G1　进程级资源预算缺失

现状

  • §4.1 仅有"限制 CPU/内存"一句；所有上限（队列、连接、码率、media.max_channels）都是符号，无数字。
  • §18 第 9 条已把"Flash/内存/CPU 预算"列为冻结项 —— 有位置，没内容。
  • v4 至少有 cgroup 配额行（§5.4）与依赖体积/可否省略表（附录 A），v5 全部删除。

风险后果：T113-S3 为 2×Cortex-A7 + 片内 128MB DDR3，需同时容纳 ivsboxd（TLS + SQLite + 状态镜像）、 HTTP 服务、FFmpeg remux 1~3 路写 SD、logd、procd、4G 拨号栈。没有量级锚点，参数会被拍脑袋，且到 M6 才会第一次真正讨论，届时改动成本最高。

建议措施

  1. 在 §18 增补"资源预算"为第 10 类冻结项，并给出附录级估算表（见本文附录 A）作为起步假设。
  2. 把 cgroup 从 §14 的"待确认组件"提回架构正文 —— 它是 media 隔离的实现手段，不是可选依赖。
  3. media.max_channels 的缺省值由预算表倒推（建议缺省 2，硬上限 3~4），不得独立配置。
  4. 同时核算文件描述符上限：探活并发 × socket + ONVIF/SNMP + IPC + 录像会话，与系统缺省 ulimit -n（常为 1024）比对。

验收方式：M1 阶段在真实 BSP 上跑空载 + 3 路录像，输出 VmRSS / VmPeak / fd 计数实测表。

G2　喂狗判据与慢任务混淆

现状

  • §4.2：慢任务池处理 SNMP、ONVIF、RTSP 能力探测、DNS。
  • §12.3："主循环或关键模块超出预算时记录最小故障信息并停止喂狗。"

风险后果：4G 弱网下 SNMP 超时、DNS 挂起、ONVIF SOAP 无响应都是正常现象。若健康判据包含"慢任务进度"，一次 30s 的 SNMP 阻塞即触发喂狗超时 → 整机复位 → 现场表现为"设备无故重启"，且日志里看不到原因（复位时来不及落盘）。

建议措施

  1. 明确写死：健康判据只看主事件循环的原子进度号 + 关键链路时间戳；慢任务只做"超时计数 + 告警"，不参与喂狗。
  2. 给出时间关系式：watchdog timeout > procd 重启间隔 + 进程启动到首次喂狗的时间，否则 ivsboxd 正常崩溃重启也会被硬件狗咬。
  3. 停止喂狗前的最小故障信息必须先 fsync 落盘（否则复位即失证据）。

验收方式：故障注入 —— 人为把 SNMP 目标指向黑洞地址（30s 超时），观察设备不复位且产生告警。

G3　非特权进程拉起 root 升级器的提权路径未定义

现状

  • §4.1 / §13.1：ivsbox-updater 为 root、按需运行；ivsbox-provision 仅工厂模式可运行。
  • 全文未说明由谁、通过什么机制启动它们。ivsboxd 是普通用户 + 少量 capabilities。
  • §11.2 的"连续启动失败计数"存储位置与防篡改也未写。

风险后果：这是全文唯一一处权限设计缺口，且正在安全关键路径上。实现者若自行发明机制（如给 ivsboxd 加 setuid 辅助程序、或让 ivsboxd 直接持 root），会把整个特权模型推翻。

建议措施

  1. 固定触发方式（推荐：procd/ubus 受限服务，或预约定路径的触发文件）。
  2. 硬约束：不可传入路径/命令参数（不接受任何来自网络或 Web 的目标路径）； ivsbox-updater 必须自行重新验签，不信任调用方的校验结果。
  3. 回滚计数落在受保护存储（如工厂分区或带签名的状态文件），并说明防篡改手段。
  4. 量产后关闭 ivsbox-provision 入口（§13.1 有方向，需给出具体机制）。

G4　Web 下载媒体文件的跨进程路径自相矛盾

现状

  • §9.1 Web 页面含"媒体：图片、录像、下载"。
  • §10.1 / §4.4：媒体文件归 ivsbox-media；ivsbox-web 是"无特权用户、不访问媒体目录"。
  • §5.1 仅含糊写了"超限数据通过文件句柄、任务 ID 或分片协议传递"。

风险后果：需求与约束直接冲突，实现者必须自行选择，选择结果会影响权限模型。

建议措施（三选一，写进架构）

方案说明代价
A（推荐）ivsbox-media 经 SCM_RIGHTS 传 fd 给 Web权限不扩散，天然支持 Range 定位；实现稍复杂
B给 Web 一个只读白名单媒体目录简单，但破坏"媒体文件唯一归 media"的声明
CWeb 反向代理到 media 自身的 127.0.0.1 HTTP 服务实现最省；media 需开监听口，须限本机 + 鉴权

同时明确"未确认数据补传队列"的文件读写权限归属。

G5　启动顺序与就绪分级未定义

现状

  • §4.1 仅"所有常驻进程由 procd 管理"；§5.1 仅"服务重启后客户端重新连接并重新订阅事件"。
  • 未定义初始化分级、启动时间预算、主控未就绪时 media/web 的重连退避。

风险后果

  1. procd 并发拉起三个常驻进程 → media/web 在 ivsboxd socket 尚不存在时连接失败 → 若无可退避重连，即 respawn 循环（冷启动打摆子）。
  2. 与 G2 联动：首次喂狗时机未定义 → 启动期可能被狗复位。
  3. §11.2 的 OTA 确认窗口（60s）若小于弱网下 L4 达成时间 → 误回滚。

建议措施：补一节"启动顺序与就绪分级"，至少按下表定义，并把两条时间约束写成硬约束。

级别内容目标时间依赖
L0核心就绪：IPC socket bind、UART 打开~2s本地
L1门禁/开锁可执行 → 首次喂狗~4sUART
L2Web 本地运维可用（可登录看状态）~8sIPC
L3双 WAN 选路 + 探活启动~12s内核/模组
L4平台连接 + 会话恢复 + 补传~20s外部网络
L5设备面首轮探测（摄像机/SNMP/ONVIF）可延迟外部设备

两条硬约束

  • watchdog timeout > L1 达成时间，首次喂狗前不得开狗；
  • OTA 确认窗口 > L4 最坏达成时间（弱网下可达数十秒）。

另需明确：L0 之前 media/web 的重连退避参数（建议指数退避 + 上限），以及"平台不可达时以 L5 之外的能力降级运行"的语义。

G6　慢任务池容量无量化验证

现状

  • §4.2："固定两个 worker……队列长度固定，满时返回忙状态。"
  • §16.1 集成测试无"多摄像机并发探测"场景。

风险后果（比"排队超时"更严重）：按 M4 现实负载估算，32 台摄像机 × （SNMP ~2s + ONVIF ~1s + RTSP 探活 ~2s）≈ 160 秒工作量/轮，2 个 worker = 80 秒墙钟。若巡检周期为 30 秒，则队列永久积压，worker 100% 时间在超时重试。此时真正的问题不是"某次探测慢"，而是探活样本被饿死 —— 双 WAN 的 fail_n/ok_n 滞回判据、自愈引擎的"连续失败 N 次"、上游同源判断全部建立在这套样本上，样本陈旧会导致 切换与重启的决策依据错误。

建议措施

  1. §16.1 增补量化场景："N 台摄像机（按现场实际路数）并发 SNMP + ONVIF + RTSP 探测"，给出 N、巡检周期、最坏单次耗时的预算表。
  2. 队列满改为丢最旧 + 计数告警，而不是只返回忙 —— 否则积压永远不可见。
  3. 对"worker 数可配"持保留意见：worker 数是并发上界，同时也是内存消耗上界，开放配置后现场必然被调大。建议改为分池 + 按轮预算限流：控制类快任务（ICMP 等）留在 Reactor，设备探测类单独成池，配合 token bucket 限流，宁可拉长周期也不允许积压。

3. P1 缺口详情

G7　模块边界无强制手段

现状：§6 给出 5 条依赖规则（全部为散文），§15 仅提到"Host：……和静态分析"。 并且这是相对 v3 的回退 —— v3 工程结构含 scripts/ci/check_layering.sh，v5 §15 只留 scripts/init.d/。

判断修正："ivsboxd 是大单体"本身不是风险。128MB 内存 + 2×A7 的板子上，继续拆进程只会让每个进程各带一份 libc/mbedTLS，并把业务状态切成跨进程事务。真正的风险是边界靠自觉。因此落点应是编译期强制，而非"拆进程"。

建议措施

  1. include/ivsbox/ 只放公共头；src/modules/<x>/ 的私有头不进公共 include 路径（目录即边界）。
  2. core / hal / 各 module 分别编成静态库，用 CMake target_link_libraries 把依赖方向写死 —— 越界直接链接失败，比扫描 include 硬得多。
  3. check_layering.sh 作为兜底重新加回并进 CI。

G8　procd respawn 无熔断

现状：§12.3 表格仅"服务级：procd respawn"。§4.1 说"主控异常由 procd 先拉起，无法恢复时由硬件看门狗复位整机"，但未定义"无法恢复"的判据。

风险后果：进程崩溃循环会被 respawn 掩盖成"设备一直在重启"，问题在日志里表现为噪音而非故障。

建议措施：设置 respawn 次数上限；超限进入 failsafe 并停止喂狗（让硬件兜底），同时产生最高级别告警。明确"无法恢复"= 单位时间内 respawn 次数超阈值。

G9　时间跳变对媒体/审计/自愈/平台的连带影响

现状：§7.7 只写了"小偏差渐进校正，大偏差在记录审计后设置，避免日志时间反复跳变"。

风险后果（外部评审提了命名与索引，实际影响面更大）

  1. 录像切片：§8.2 按 1~5 分钟切片，若文件名含本地时间，时钟回跳会造成文件名乱序甚至覆盖。
  2. media.db 索引：§10.3 未规定 ts 字段时区，回跳会造成区间查询错乱。
  3. TLS 时间死锁（最严重）：设备上电时 RTC 未同步 → 时间回到 1970 或默认值 → 证书有效期校验失败（"certificate not yet valid"）→ 平台连不上 → NTP/平台授时也拿不到 → 永久无法自愈。这是一个鸡生蛋的死锁，必须在设计上打破。
  4. 自愈熔断失效：§7.6 的"冷却、每小时/每天上限、时间窗口"全部依赖墙钟。时钟跳变会让频率限制算错 —— 可能绕过熔断造成重启风暴，也可能误熔断。
  5. 门禁开锁的"有效期"、隧道 token 的 ttl_s、审计时间戳同样依赖时钟。

建议措施

  1. 分离时钟：所有时长、窗口、超时、退避一律用 CLOCK_MONOTONIC；墙钟只用于"给人看的时间戳"和证书校验。
  2. 墙钟增加"可信标志"：未同步前，媒体索引存"UTC + 单调计数"双字段，切片文件名用单调序号而非本地时间。
  3. 时间不可信时放宽 TLS 证书时间校验（仅限时间维度，不得放宽链与主机名校验），或预置平台证书的时间容错窗口，明确记录该降级的审计。
  4. 大偏差跳变前先归档当前媒体索引批次，避免跨批次查询错乱。

G10　现场诊断能力缺失

现状

  1. core dump：v4 有（"core dump 留证"），v5 §12.1 全部删除，且 §13.1 权限表未涉及。
  2. 远程取证通道：§9.4 白名单只列了 web、camera:<id>、media:<id>， 没有日志/状态取证服务名 —— 断网录像出问题时无法远程取证。

建议措施

  1. 补 core dump 策略：是否启用、存放路径（建议 /mnt/UDISK/ivsbox/core/）、单个大小上限、总配额与滚动策略、是否随故障日志上报。
  2. §9.4 白名单增补只读诊断服务名（如 log / diag），并明确： 只读、限速、有大小上限、不提供 shell、全部操作记审计。
  3. 明确"media 崩溃/录像异常"场景的取证步骤（这是最容易现场扯皮的一类故障）。

G11　五类版本缺兼容矩阵

现状：§5.1 定义了 IPC 协议版本，§10.2 定义了配置 schema 版本，但无统一视图。 §4.2 未定义 IPC 版本不匹配时的行为（拒绝并告警 vs 静默降级）。

建议措施：补一张兼容矩阵，覆盖 IPC / DB schema / 配置 schema / 平台协议 / 采集板协议 五类版本，并明确三条规则：

  1. 三个常驻进程必须同 release、整体重启；
  2. IPC 版本不匹配 → 拒绝连接并告警，不得静默降级；
  3. DB / 配置 schema 升级必须向前兼容一个版本（可读旧、写新）。

G12　错误码字典 / IPC 方法 ID 未进 §18 冻结项

现状：§9.2 说"API 返回稳定错误码"，§7.1 提到"失败细分码"，但全文无错误码表； §5.2 只列了若干典型方法名，无完整方法 ID 表。§18 的 9 类冻结项未包含这两项。

建议措施：把"错误码字典（探活失败细分码 + 平台/业务错误码 + IPC 错误码）" 与"IPC 方法 ID 表"补入 §18 冻结项，与平台协议、UART 协议同级别管理。
