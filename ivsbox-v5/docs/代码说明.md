## 2026-09-23 17:15　修复 -std=c11 下 POSIX 声明缺失导致的 ARM 构建失败

- **涉及文件**：`ivsbox-v5/CMakeLists.txt`（修改）
- **干了什么事**：在顶层 `CMakeLists.txt` 中 `add_compile_options(-Werror)` 之后、`set(IVSBOX_INCLUDE_DIR ...)`
  之前插入 4 行：

  ```cmake
  if(UNIX)
      add_compile_definitions(_GNU_SOURCE)
  endif()
  ```

  即在 Linux（板端 + Linux 主机）构建时，给所有目标追加 `-D_GNU_SOURCE`。
  因为写在顶层且位于各 `add_library` / `add_executable` / `add_subdirectory` 之前，
  故对 `ivcore`、`ivhal`、`ivsboxd` 以及 `media`、`web`、`updater`、`tools`、`tests` 全部生效。
  没有任何源文件被改动。

- **解决什么问题**：
  - **现象（使用者实测）**：

    ```text
    src/core/iv_log.c:43:9: 错误： implicit declaration of function ‘clock_gettime’; did you mean ‘localtime’?
    src/core/iv_log.c:43:23: 错误： ‘CLOCK_MONOTONIC’未声明(在此函数内第一次使用)
    cc1：所有的警告都被当作是错误
    ```

  - **根因**：顶层 `CMakeLists.txt` 设了 `CMAKE_C_EXTENSIONS OFF`，CMake 因此传 `-std=c11`。
    严格 ISO C 模式下编译器会定义 `__STRICT_ANSI__`，glibc 的 `features.h` 于是不启用
    `_DEFAULT_SOURCE`，也就不暴露 `clock_gettime` / `CLOCK_MONOTONIC` 这些 POSIX 声明；
    再叠加 `-Werror`，隐式声明直接升级为编译错误。
  - **不止这一个文件**：`src/hal/iv_clock.c:23` 用同一组接口，只是编译顺序在后还没轮到；
    S03 要用的 `epoll` / `timerfd` / `signalfd` / `accept4` 同属这一类，
    不在此处一次性解决，后面每个模块都要重踩一遍。
  - **改后**：`__linux__` 分支能正常取到声明，`iv_log.c`、`iv_clock.c` 编译通过，
    全量 ARM 构建（含链接）成功产出 `ivsboxd`。

- **为什么这么做**：
  - 在**构建层**统一加宏，而不是在每个 `.c` 里手写 `#define _GNU_SOURCE`：
    后者必须写在所有 `#include` 之前，容易漏写、也容易被格式化或后续编辑挪位；
    且每新增一个用 POSIX 接口的文件都要重复一次。
  - 选 `_GNU_SOURCE` 而不是 `_POSIX_C_SOURCE=200809L`：`clock_gettime` 只需 POSIX 2008，
    但 S03 的 `signalfd` / `accept4` 在 glibc 下属 GNU 扩展，一次到位避免二次返工。
  - 用 `if(UNIX)` 包住：Windows(MinGW) 主机侧走源码里的 `#else` 分支
    （`log_mono_seconds()` 返回 0.0、`iv_clock_mono_ms()` 回退墙钟），本就不需要该宏，
    保持其行为与既有验证结果不变。
  - **被否掉的方案**：① 把 `CMAKE_C_EXTENSIONS` 改为 `ON`（等价 `-std=gnu11`）——能编译过，
    但等于放弃"严格 ISO C + 显式声明特性宏"这条纪律，并一并放开其它 GNU 方言；
    ② 在源码内逐个 `#define _GNU_SOURCE`——分散且易漏。

- **影响范围**：
  - 板端（`cmake/toolchains/tina-arm.cmake`）与 Linux 主机（`build/host`）的全部 C 目标获得 `-D_GNU_SOURCE`；
    Windows(MinGW) 主机不受影响。
  - 工具链文件本身未改动；编译产物的 ABI 不变（只影响可见声明集合），不影响上板兼容性。
  - 未覆盖：本改动只解决"声明可见性"，不涉及运行期行为；`iv_log.c` 的 Windows 分支仍返回 0.0。
  - 未覆盖：`-Werror` 下 S02/S03 新代码仍可能触发其它警告，属正常开发流程，不由本改动兜底。

- **验证方式与结果**：在 `tqt113`（192.168.2.115，天嵌 TQT113 编译 VM）上做两级验证。

  第一级——定位根因、确认宏的必要性与充分性（对已 clone 的源码逐文件编译，输出丢弃到 `/dev/null`）：

  ```sh
  TOOL=/opt/EmbedSky/Tina/bin/arm-linux-gnueabi-
  SRC=/home/embedsky/work/T113_S4/ivsbox-v5

  # (A) 复现：不带特性宏 → 与使用者报错完全一致
  ${TOOL}gcc -std=c11 -Wall -Werror -I$SRC/include -c $SRC/src/core/iv_log.c -o /dev/null
  #  -> iv_log.c:43:9  错误： implicit declaration of function 'clock_gettime'
  #  -> iv_log.c:43:23 错误： 'CLOCK_MONOTONIC'未声明
  ${TOOL}gcc -std=c11 -Wall -Werror -I$SRC/include -c $SRC/src/hal/iv_clock.c -o /dev/null
  #  -> iv_clock.c:23 同样报错（确认不止一个文件受影响）

  # (B) 修复：带 -D_GNU_SOURCE → 无输出、退出码 0
  ${TOOL}gcc -std=c11 -D_GNU_SOURCE -Wall -Werror -I$SRC/include -c $SRC/src/core/iv_log.c -o /dev/null
  ${TOOL}gcc -std=c11 -D_GNU_SOURCE -Wall -Werror -I$SRC/include -c $SRC/src/hal/iv_clock.c -o /dev/null
  ```

  第二级——全量交叉构建（构建目录放 `/tmp`，不污染仓库）：

  ```sh
  cmake -S $SRC -B /tmp/ivs-build-check \
        -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/tina-arm.cmake \
        -DIVSBOX_BUILD_TESTS=OFF -DCMAKE_BUILD_TYPE=Release \
        -DCMAKE_C_FLAGS="-D_GNU_SOURCE"      # 与本次改动等价的那条宏
  cmake --build /tmp/ivs-build-check -j
  ```

  实测结果：

  - `configure_exit=0`；日志含 `-- ivsbox: sysroot = /opt/EmbedSky/Tina/arm-buildroot-linux-gnueabi/sysroot`、
    `-- The C compiler identification is GNU 7.3.1`；
  - `build_exit=0`；`libivcore.a`、`libivhal.a`、`ivsboxd`、`ivsbox-media`、`ivsbox-web`、
    `ivsbox-updater`、`ivsbox-provision` 全部构建成功；
  - `file /tmp/ivs-build-check/ivsboxd` →
    `ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux.so.3, for GNU/Linux 3.2.0`；
    `readelf -h` 显示 `类别: ELF32`、`系统架构: ARM`；大小 20716 字节；
  - 验证后 `rm -rf /tmp/ivs-build-check`，`/tmp` 无残留。

  **说明与遗留**：第二级用的是 `-DCMAKE_C_FLAGS="-D_GNU_SOURCE"` 等价参数（因为 VM 上的 clone 还在
  改动之前的提交上），命令行的合成结果与 `add_compile_definitions(_GNU_SOURCE)` 相同。
  **改动落地后仍待使用者在本机重新 `cmake --build` 复核一次**；上板运行尚未进行，
  故 `docs/IVSBox-功能开发列表.md` 中 S01 的状态仍保持"未实现"。

## 2026-09-23 16:15　交叉编译工具链文件对齐实测环境

- **涉及文件**：`ivsbox-v5/cmake/toolchains/tina-arm.cmake`（修改）
- **干了什么事**：只改这一个文件，三处改动。

  1. **工具链前缀默认值**：`arm-openwrt-linux-` → `arm-linux-gnueabi-`
     （`IVSBOX_CROSS_PREFIX` 缓存变量保留，仍可用 `-DIVSBOX_CROSS_PREFIX=...` 覆盖）
  2. **新增 `IVSBOX_SYSROOT` 缓存变量**，默认 `/opt/EmbedSky/Tina/arm-buildroot-linux-gnueabi/sysroot`
  3. **sysroot 解析改为三级，不再致命**：
     - ① `IVSBOX_SYSROOT` 指向的目录存在 → 用它
     - ② 否则若已导出 `TINA_SDK_ROOT` → 用 `$TINA_SDK_ROOT/out/t113/staging_dir/target`
     - ③ 都不可用 → 只 `WARNING` 并退回工具链自带 sysroot，配置继续
     - 删除原来"未设置 `TINA_SDK_ROOT` 就 `FATAL_ERROR`"的分支
     - 命中 sysroot 时同时设置 `CMAKE_SYSROOT` 与 `CMAKE_FIND_ROOT_PATH`，
       并删掉文件下方重复设置 `CMAKE_FIND_ROOT_PATH` 的那一行

  数据流很简单：这个文件只决定两件事——**用哪个前缀去调 gcc**、**头文件和库去哪个 sysroot 找**。
  其余（`-Werror` 等编译选项、Release 优化参数、板端关闭测试）未动。

- **解决什么问题**：
  - **改动前**：脚本按"全志原厂 OpenWrt SDK"的假设写死了两处平台事实——前缀 `arm-openwrt-linux-`、
    sysroot 为 `${TINA_SDK_ROOT}/out/t113/staging_dir/target`，且未导出 `TINA_SDK_ROOT` 时直接中断配置。
  - **实际环境**（2026-09-23 在天嵌 TQT113 编译 VM 上实测）与该假设不符：

    | 项 | 实测值 |
    |---|---|
    | 工具链前缀 | `arm-linux-gnueabi-` |
    | 编译器 | gcc 7.3.1（Linaro 7.3-2018.05），`--with-float=soft --with-arch=armv7-a --with-tune=cortex-a9` |
    | 安装位置 | `/opt/EmbedSky/Tina/`（`bin/` 下是转发脚本，实体在 `opt/ext-toolchain/bin/`） |
    | sysroot | `/opt/EmbedSky/Tina/arm-buildroot-linux-gnueabi/sysroot`（glibc 2.25） |
    | Tina SDK | **不存在**，没有 `staging_dir` |

  - 结论：照原脚本执行必然配置失败（前缀找不到编译器 + `TINA_SDK_ROOT` 致命检查）。
  - **改动后**：默认参数即匹配当前实测环境，配置命令无需附加 `-D` 参数；
    同时保留原厂 Tina SDK 路线（导出 `TINA_SDK_ROOT`，或 `-DIVSBOX_SYSROOT=` 显式指定）。

- **为什么这么做**：
  - 选"改默认值 + 保留覆盖入口"，而不是"让使用者每次手敲一长串 `-D`"：
    当前只有一台实测可用的编译机，默认值贴合现实，出错面最小。
  - 把 `TINA_SDK_ROOT` 从致命检查降级为候选路径，而不是删除该分支：
    后续若换用全志原厂 SDK，仍可零改动复用同一份工具链文件。
  - 不追加 `-mfloat-abi=soft`：该工具链 configure 阶段已 `--with-float=soft`，
    实测不指定也能编出正确的软浮点目标，加了反而是在重复约束。
  - 被否掉的方案：把 sysroot 路径写死到 `CMAKE_FIND_ROOT_PATH` 而不设 `CMAKE_SYSROOT`——
    实测该工具链 `-print-sysroot` 的结果就是同一目录，显式设置 `CMAKE_SYSROOT` 让语义更清楚，故采用。

- **影响范围**：**只影响板端（ARM）构建**，即 `-DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/tina-arm.cmake`。
  主机侧 `build/host` 不使用该工具链文件，单测与 fuzz 不受影响。
  默认值变更后，在其他环境（原厂 Tina SDK / musl）上构建必须先显式 `-DIVSBOX_CROSS_PREFIX=...`。
  未改动：`CMAKE_C_FLAGS_RELEASE`（`-O2 -g -ffunction-sections -fdata-sections`）、
  `CMAKE_EXE_LINKER_FLAGS_RELEASE`（`-Wl,--gc-sections`）、`IVSBOX_BUILD_TESTS OFF`。

- **未覆盖 / 风险**：
  - 架构与浮点 ABI 是否与板端 rootfs 完全一致，**尚未在真实板子上验证**。
  - sysroot 内 glibc 为 **2.25**，与天嵌《应用开发手册》中"需要 glibc 2.34"的说法不一致；
    以实测为准，但板端 rootfs 的 libc 版本**仍需上板比对**。
  - 工具链是 buildroot + glibc，而非项目文档假设的 OpenWrt + musl；
    这对 S02（logd）、S17（uhttpd）、S18（procd respawn）、S20（ipk 打包）的技术选型有影响，
    须待 `scripts/bsp-survey.sh` 在板端实测定性，**当前只登记为待确认，不下结论**。
  - cmake 尚未在该 VM 安装，因此"经 cmake 实际跑通"这一步**尚未验证**。

- **验证方式与结果**：在 `tqt113`（192.168.2.115，Ubuntu 22.04.2 x86_64，用户 embedsky）上执行：

  ```sh
  TOOL=/opt/EmbedSky/Tina/bin/arm-linux-gnueabi-
  SYSROOT=/opt/EmbedSky/Tina/arm-buildroot-linux-gnueabi/sysroot

  # 1) 工具链自身默认 sysroot（用于核对脚本默认值）
  ${TOOL}gcc -print-sysroot
  # -> /opt/EmbedSky/Tina/arm-buildroot-linux-gnueabi/sysroot

  ${TOOL}gcc -print-file-name=libc.so.6
  # -> /opt/EmbedSky/Tina/arm-buildroot-linux-gnueabi/sysroot/lib/libc.so.6

  # 2) 用该前缀 + sysroot 编译最小程序
  #    结果：compile_exit=0
  ${TOOL}gcc --sysroot=$SYSROOT -O2 -Wall -o /tmp/ivs_probe /tmp/ivs_probe.c

  # 3) 检查产物 ABI
  file /tmp/ivs_probe
  # -> ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV), dynamically linked,
  #    interpreter /lib/ld-linux.so.3, for GNU/Linux 3.2.0

  ${TOOL}readelf -l /tmp/ivs_probe | grep -A1 INTERP
  # -> [Requesting program interpreter: /lib/ld-linux.so.3]
  ```

  **结论**：

  1. 前缀 `arm-linux-gnueabi-` 可用，产物为 ARM EABI5 32 位 ELF。
  2. 脚本默认 sysroot 与工具链 `-print-sysroot` 输出**完全一致**，默认值正确。
  3. 产物解释器为 `/lib/ld-linux.so.3`，由 sysroot 中的 `ld-2.25.so` 提供 →
     **板端 rootfs 必须存在 `/lib/ld-linux.so.3` 且 libc 与 2.25 兼容**；
     这是 S01 上板的第一项检查，若有偏差此即根因。
  4. 临时文件（VM 侧 `/tmp/ivs_probe*`、`/tmp/ivsbox-verify`）已删除。

  **尚未验证**：`cmake -S . -B build/arm -DCMAKE_TOOLCHAIN_FILE=...` 的完整配置与 `ivsboxd` 编译，
  以及上板运行。前置条件是：VM 安装 cmake、源码进入 VM（计划走 git clone）。
