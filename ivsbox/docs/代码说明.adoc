- *口径变更（用户 2026-10-09 拍板）*：S2.4 *只做协议不做传输*——TCP 连接/断线重连/出口切换整体移 M3 网络管理，本层经 `on_tx` 回调＋`iv_proto_recv()` 与传输层解耦。这样协议层可独立完成并用字节级注入验证，M3 实现后只需接一个传输后端。
- *实现中真 bug（被自己的单测抓出）*：帧头锁定路径预写了*两个*帧头字节，随后的统一 `buf[pos++]=d` 又把当前字节（帧头第二字节）追加进去 ⇒ 帧体整体偏移 +1、CRC 全错、所有解析用例失败。修正为预写只落帧头*第一*字节（MCU 参考实现同款写法）。教训：帧头"滑动窗口 + 预写"的写法必须显式数清预写字节数与当前字节的关系。
- *CRC 错帧静默丢弃（不回错误帧）的设计取舍*：平台走 TCP/4G，链路层已保证可靠传输，CRC 错基本意味着流内损坏或攻击；回错误帧会让对端把噪声当有效交互，放大流量。参考实现对 CRC 错的处理就是"执行结束"（不回），本层一致。

=== 解决什么问题

- 此前 `ivsboxd` 没有任何配置来源：参数只能硬编码或编译期注入。本步之后运行参数可从 `/mnt/UDISK/ivsbox/config/` 读、可写回、可在不重启的前提下随文件变化生效。
- *`crc` 不符只告警不拒绝*：手工编辑（正是 F6 的典型路径）必然让 `crc` 过期；若"校验不过就拒绝加载"，等于把"改配置"变成"停服"。因此 `crc` 只用于发现损坏与提醒，下次 `save()` 自动刷新。
- *启动期与运行期对"非法值"的处置刻意不同*：`open()` 逐键回退默认并计入 `invalid`（此时没有"旧配置"可留，必须照常启动 —— F4）；`watch_poll()` 只要出现任一非法值或解析失败就*整份拒绝*、旧值一字不动、一个订阅者都不通知（半新半旧比全旧更危险 —— F6/F7）。
- *实现过程中自行发现并修掉的 5 个缺陷*（写完即逐行复核时抓到，未流出到提交），其中两个是真功能缺陷：
  1. *热更新会把配置静默清空（F6 真违反）*：文件写成 `{"net": 5}`（子树写成标量）时，默认表补不进去、又不存在"非法值"，于是整份被当成合法配置接受 ⇒ `net.*` 全丢。修法：新增 `is_default_parent()`，凡占着已知键父路径的标量键一律判非法并剔除，随后默认子树正常补齐；热更新侧也因 `invalid>0` 而拒绝。
  2. *`iv_config_secure_read()` 静默截断*：缓冲放不下时截断后返回 `IV_OK`，会给出一个"看起来合法、实际错误"的令牌。修法：读满 `cap-1` 后再探一字节，能读到即 `IV_ERANGE`。
  3. 头文件注释块被 `set_*/save()` 里的 `*/` 提前闭合 → 整份头文件解析错乱、报一串"unused parameter"假错。修法：改写该句避开 `*/`。

- *open 流程*：`open(O_RDWR|O_NOCTTY|O_NONBLOCK|O_CLOEXEC)` → `flock(LOCK_EX|LOCK_NB)` → `isatty()` 校验 → `cfmakeraw` → 清 `CRTSCTS`／置 `CLOCAL|CREAD`／按 cfg 设 `CSIZE`、`PARENB|PARODD`、`CSTOPB`、`VMIN=0`、`VTIME=0` → `cfsetispeed/cfsetospeed` → `tcsetattr(TCSANOW)` → `tcflush(TCIOFLUSH)`。顺序不能换：`cfmakeraw` 会把 `CSIZE` 一起清掉。
- *两个语义要点*：① `read` 把 `read()==0` 翻译成 `IV_EAGAIN`（`VMIN=0` 下 0 表示"当前没数据"，*不是 EOF* —— 串口没有"连接"概念，误判成断链会很难查）；② `write` 是*字节流*语义，返回*实际写入字节数*（可能小于请求长度，调用方续写），与 `iv_chan_send()` 的整包语义刻意不同。

=== 实现中修掉的真缺陷（细节）

`nl_route_one()` 发 `RTM_DELROUTE`/`RTM_NEWROUTE` 时，`nlmsg_flags` 只设了 `NLM_F_REQUEST`（NEWROUTE 另加 `NLM_F_CREATE|NLM_F_REPLACE`），*没有 `NLM_F_ACK`*；但函数之后做*阻塞 `recv()`* 等 ack。netlink 的约定是：*不带 `NLM_F_ACK` 时，只在出错才回消息*。因此当操作*成功*（即绝大多数正常路径），内核根本不回包，`recv()` *永久阻塞*，网络管理线程（进而整机业务）卡死。

*为何此前一直没被发现*：在 Windows/宿主上，`real_switch_route` 拿到的 ifindex 往往是 0（没有真网卡），`nl_route_one` 在 `sendmsg` *之前*就 `return IV_EINVAL` 了，压根走不到 `recv`；单测又是注入式假 I/O，更碰不到 netlink。一旦在 netns 里用*真实网卡*，第一次成功切换即挂死 —— 临时驱动 `nm_real` 被 `timeout` 杀掉就是证据。

*修复*：`NLM_F_REQUEST | NLM_F_ACK`（NEWROUTE 再加 `CREATE|REPLACE`）；并给 socket 加 `SO_RCVTIMEO`(1 s) 作兜底，使极端情况下退化为"事务失败 ＋ 5 s 重试窗口"，而不是永久阻塞。

=== 板端验证口径（与 VM 的差异，务必记牢）

板子只有 `eth0` 一条*可用* WAN（`usb0` 无拨号脚本、当前 DOWN），把默认出口真切过去会*切断唯一管理链路*；故板端只做*安全*的真机验证：让状态机"切到 eth0"，实际效果是*新增一条同样指向 `eth0` 的 `metric 100` 默认路由*（DHCP 的 `metric 204` 那条与 `192.168.2.0/24` 直连路由都不动，SSH 走直连路由，不受影响），验完即删并确认还原。*"真切换"的等价证据由 VM netns 提供*。

=== 关键：判据是 `UP && RUNNING`，不是 `UP && LOWER_UP`（被实测逼出来的）

- *`struct ifreq.ifr_flags` 是 `short`（2 B）*，而 `IFF_LOWER_UP = 0x10000` —— `SIOCGIFFLAGS` **结构上装不下那一位**。原方案（本日 A 项拍板）写的是"与事件路径完全同源 ＝ `IFF_UP && IFF_LOWER_UP`"，实测证明**做不到**。
- *板端证据（TQ113，内核 5.4.61-rt37）*：`eth0`/`usb0` 有载波时 `ioctl` 回 `0x1043`（UP｜BROADCAST｜MULTICAST｜**RUNNING**，`LOWER_UP` 恒 0），而**同一时刻** `ip` 报 `<BROADCAST,MULTICAST,UP,LOWER_UP>`（该位只有 32 位的 netlink `ifi_flags` 才有）。
- *`/sys/class/net/<if>/flags` 同样不能替代*：板端回 `0x1003`（UP｜BROADCAST｜MULTICAST，既无 `LOWER_UP` 也无 `RUNNING`）；VM 私有 netns 里该文件**根本不存在**。
- *`IFF_RUNNING` 是等价代理*：它是内核 `dev_get_flags()` 按 RFC2863 合成的"操作态 up"（`netif_running && netif_oper_up`），在**已测全部场景**与 `LOWER_UP` 逐一致：板端 `eth0`/`usb0` → 1（与事件路径同）；VM netns dummy `ip link set up` → `0xc3` → 1、`set down` → `0x82` → 0（`ip` 也分别报 `LOWER_UP` / 无）。
- *⇒ 如实写明"语义等价代理"而**非**"完全同源"*：`iv_netlink.c` 新增 `IVNL_KF_RUNNING` 常量并在 `iv_netlink_link_up()` 上方写清"两条路径为什么用的位不同源"，`iv_netlink.h` 的 API 注释同步；`test_netlink.c` 的 c13 注释与 oracle 取位（只用 `IFF_UP`）也照这一事实改写。**不假装同源是本轮刻意保留的诚实性。**

* 后果：串口是**字节流、没有消息边界**。采集板若发到一半掉电/复位（帧头与长度域已收到、data 没收全），状态机就停在 `ST_DATA`；此后每一帧的正常字节 —— 连同步字 `0F0F` 也算 —— 都被当成上一帧的 data 吃掉（data 满 1024 字节后判 `too_long` 回搜索态，但那时已经吞掉约 1 KB 的有效数据/多帧），**串口链路实际上永久失效，只能重启进程**。计划 §0.1 自 2026-10-10 起把这条登记为遗留。
* 改动后：`iv_link_tick()` 每次被调用（装配层 200 ms 总线节拍）都顺手做一次帧超时检查；半截帧超过 `gap_ms` 即复位回同步搜索态，**紧随其后的完整帧恢复正常接收**。复位只丢残帧、不回调上层，在飞事务照原样由 `timeout_ms` 重传兜底 ⇒ 与既有的"命令级确认 ＋ 超时重传"语义正交、不冲突。

=== 关键取值与硬约束（写进头文件，避免后人改坏）

* **`gap_ms` 必须 > `iv_link_tick()` 的调用周期**。装配层 `iv_report_step()` 由 `IV_AGENT_PROBE_TICK_MS = 200 ms` 定时器驱动；串口一次 `read` 可能只取到半帧，剩余字节要等下一次节拍才喂进来 —— `gap` 若小于节拍，"被节拍切开的正常帧"会被误判成半截帧丢掉。
* 默认 **500 ms**：单帧线上时间 @115200 约 23 ms（`IV_FRAME_MAX` = 8 ＋ 1024 B），余量充足；帧间长空闲（0xE1 轮询 30 s、上报 300 s）**不受影响** —— 复位判据要求状态机不在同步字搜索态，帧间的搜索态不会被判超时。
* 可观测性：复位次数经 `iv_framer_stats()->resets` 读取，是现场判断"采集板是否在发半帧"的唯一指标（真采集板接 `ttySAC5` 时可用它直接观察）。

=== 影响范围

* **产品默认行为变化**：帧超时由关变开。但只影响**异常半帧** —— 正常帧在字节收齐瞬间即交付并回到搜索态，不受影响；E2E（假采集板 pty）与板端真串口路径均无变化。
* `gap_ms` **未接配置键**：走编译期默认 500 ms。配置化属于"装配层配置接线"的范畴（`iv_link` 在模块层，不读配置），本轮刻意不做。
* 既有单测/fuzz 的语义**逐字不变**（它们的 cfg 位置初始化补 `0u` ＝ 关闭，与改动前一致）；新增覆盖只在第 12 组用例。

== 2026-10-13 13:14 M4-S4.4 摄像机/主网故障断电重启（0xD1 ＋ 待发 FIFO）

=== 干了什么事

* *新增自愈模块 `ivsbox/src/modules/recovery/iv_recovery.c`（＋ `include/ivsbox/iv_recovery.h`，零 malloc、无 fd/线程/时钟依赖）*：把"网络状态从**正常(1)** 变 **故障(2)** 的**单沿**"翻成"采集板电源通道**断电 5 s 再上电**"。**只有这一点功能** —— 没有规则引擎 / 上游关联 / 熔断状态机 / 每小时每天限频（架构 §7.6 那套是旧演绎，现网没有，2026-10-13 作废）。
* *动作映射（硬口径）*：主网（MN 两路**任一**）1→2 ⇒ **继电器 1**（port 0）；**任一**摄像机（CNS 六路任一）1→2 ⇒ **继电器 2~8 全部**（port 1~7，**整排重启、不定位单台**）。依据《智能箱通用功能统计.xlsx》"功能说明"第 13 条："设备自动重启｜网络故障后，自动重启**所有输出端口**"。
* *触发判据（硬口径，逐字对齐参考 `det.c: det_main_network_and_camera_network()`）*：只有 `old == 1 && new == 2`。`0→2`（开机就是坏的 ⇒ 避免上电风暴）、`4→2` / `5→2`（延时/丢包 → 故障）、`1→4` / `1→5`（劣化）、`2→1`（恢复）**一律不触发**。
* *载荷*：`0xD1`（`IV_FRAME_CMD_POWER`）＋ JSON `{"port":<0~7>,"status":<0 关/1 开/2 重启>}` —— 架构 §18.2 冻结格式，**逐字**发射。本模块只发 `status=0`（OFF）与 5 s 后的 `status=1`（ON）；`status=2`（采集板侧 15 s 断电）留给"系统操作"的人工单通道重启，本步不用。
* *装配接线*：`iv_report` 新增通用下行出口 `iv_report_send_cmd()`（**本层自持 `iv_link`，装配层不得另持第二份**，否则"同 cmd 在飞唯一"被绕过）；`iv_agent` 内嵌 `iv_recovery_t`，把 `iv_camdet_cfg_t::on_change` **直接**接到 `iv_recovery_on_camera_change()`（签名同构、零胶水层），动作出口 `agent_send_power()` 走 `iv_report_send_cmd()`；`iv_agent_step()`（无 reactor）与 `on_pb_timer()`（reactor 200 ms 节拍）**两处**都驱动 `iv_recovery_tick()`。`main.c` 读 `netthr.reboot_max` / `netthr.reboot_interval_s`。

=== 解决什么问题

* *把"网络故障"变成"可自愈"*：摄像机掉线不再只能等人工上站 —— 采集板侧继电器**断电 5 s 再上电**是现场最有效的复位手段（现网产品的既有做法），本步把它在新架构里落下来（`0xD1` 走 UART，继电器仍在采集板侧）。
* *不让自愈变成"折腾设备"*：**单沿 + 冷却 + 限次**三把闸门保证"一次故障只处理有限次"，且**恢复后不触发**、**开机即坏不触发**（`0→2` 不动作）。**冷却期内不重复动作**、**限次耗尽只告警**（`reboot_max=0` 更是整段禁用）。
* *`iv_link` 的"同 cmd 在飞唯一"与"整排 7 条"的冲突（本步最关键的一个坑）*：一次摄像机故障要发 **7 条** 0xD1，但 `iv_link` 的配对规则**同 cmd 只允许一笔在飞**（第二笔 `IV_EBUSY`），连发 7 条只会有第 1 条被接受 —— 若不处理，**"整排重启"会在第 2 个通道上静默失败**。解法＝模块自持 **16 槽待发 FIFO**、`iv_recovery_tick()` **每拍最多下发 1 条**、`IV_EBUSY` 时**保留队头下一拍再试**。这是"串行化"的全部机制，**不需要"在飞完成回调"式的耦合**；该现象已被 r12（真 `iv_link`）与集成 c02b（假采集板 pty）**双向复现**，因此**不是过度设计**。
  * *代价（登记）*：`0xD1` 是控制命令（`iv_link` 只发一次、不重传），故"断电 5 s"是**近似值**＝"OFF 发出 ＋ 5 s ＋ 队内等待"；整排场景下各通道错开约一拍（200 ms）。
* *两处对现网代码**有意不照抄**（已登记，不是偷工）*：① 参考 `app_sys_net_relay_reload_num_times()` 在冷却结束后会**自动重新武装**同一通道（一次故障沿连做 N 轮，**不管网络是否已恢复**）；② 参考 `net_reload_num[]` **全程无复位点** ⇒ 一轮用尽后该通道**永久锁死**到下次重启。本模块改为"**只由新的故障沿驱动**"（网络已恢复就不会白白断电摄像头）＋"限次＝剩余次数，可复位"。**另**：参考 `det.c` 当前只对 `RELAY_2`/`RELAY_3` 动作（非整排），本步按**计划 ＋ 需求文档**做成整排 ⇒ 差异登记。
