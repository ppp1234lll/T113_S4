## 2026-09-29 15:57 S1–S7 审查问题闭环

### 干了什么事

- 构建：修复 `Makefile` 的 `package` 与 `analyze` 变量上下文。`package` 在 ARM 子 make 中归集产物，并逐个固定 `LC_ALL=C` 后用 `readelf` 断言 ELF Machine，避免中文工具链输出导致正确 ARM 包被误判，也避免只抽检一个产物；`analyze` 在 `BUILD_DIR=build/analyze` 的子 make 中展开应用目标。
- 日志/版本：`iv_log.c/.h` 用 C11 `atomic_flag` 串行化可变状态，ident 改为内部拷贝，root 查询改为输出缓冲快照；日志清理改用 `openat/unlinkat` 且不跟随符号链接，风暴窗口改用单调时钟，增加默认 1 MiB/小时文件上限。`iv_version.c/.h` 把版本串改成预处理期只读常量。

- 任务池/健康线程：`iv_taskpool.c/.h` 检查 mutex/cond 属性及信号掩码初始化返回值，修正 `pthread_sigmask()` 错误码来源；增加 `iv_task_heartbeat()`、worker 正在执行的槽位和 deadline 快照。`iv_health.c/.h` 对未超过 deadline 的有界阻塞任务给予健康租约，对无界长任务仍要求心跳；watchdog 连续 I/O 失败达阈值后关 fd 并把计数/故障位写入快照。
- 本地通道：`iv_chan.c/.h` 在 listen 成功时按 fd 登记 path+dev+ino，close 时只核销对应 fd 且只删除身份仍一致的 socket；完善失败清理的 errno 保存/恢复；头文件明确当前没有 SCM_RIGHTS 传 fd 实现。
- 单测：扩展 `test_log.c`、`test_reactor.c`、`test_taskpool.c`、`test_health.c`、`test_chan.c`、`test_version.c`，增加并发竞争、日期名 symlink 越界清理、句柄越权、心跳/deadline 租约、watchdog I/O fail-stop、监听点身份替换与版本串并发读取等回归。

### 解决什么问题

本次闭环 `.stint/S1-S7审查问题清单-临时.md` 的 16 项：防止把 Host 产物当 ARM 包、消除日志/版本/Reactor 的数据竞争、阻断日志符号链接越界删除和无界写盘、收紧 Reactor 句柄生命周期/归属与 timerfd 错误处理、避免合法慢任务被误判为 worker 死锁、使 watchdog 写入失败可诊断且进入 fail-stop，并防止旧监听 fd 删除后来替换的路径对象。验证过程还额外发现并修复了 `make analyze` 目标路径错位。

### 影响范围

- `iv_log_get_root()` 由返回内部指针改为 `int iv_log_get_root(char *out, size_t cap)`，后续调用者必须提供缓冲；当前仓库仅单测调用，已全部同步。
- 日志默认落点现依赖 `/mnt/UDISK` 已挂载；S10 的 init 脚本必须排在 `S60mount_udisk` 之后。挂载失败时日志模块会保持“落盘失败不阻断主程序”的原有降级语义。
- timer cancel 后不得重复使用旧指针。这是公开契约收紧，后续模块必须在 cancel 成功后立即将自己的句柄置 NULL。
- 有界阻塞任务的 `timeout_ms` 同时是健康租约，设得过长会延后卡死判定；必须用真实最坏耗时加合理余量，不能用无限大预算遮蔽故障。
- 监听点身份表定长 8 项；表满或无法取得身份时采用“宁可漏删残留，绝不误删新对象”的保守策略。listen 侧仍会重建同路径的残留 socket，S10 的单实例锁仍是必要防线。
- 本轮未进行板端运行；已完成 ARM 交叉编译。涉及真实 `/dev/watchdog` 的既有板端结论未被改动，新用例只用 pipe 模拟，不会触发板子复位。

## 2026-09-29 17:29 M1-S8 配置模块

### 干了什么事

- **新增三个文件 + 两份样本**：
  - `include/ivsbox/iv_config.h`：对外接口。**不暴露任何 json-c 类型**，调用方不需要 include json-c。
  - `src/modules/config/iv_config.c`：实现，进 `libivmodules.a`；全工程唯一 `#include <json-c/json.h>` 的文件。
  - `tests/unit/test_config.c`：14 组用例覆盖 F1~F8。
  - `config/platform.json`、`config/network.json`：配置样本（样本故意不写 `crc`，见下）。
- **数据流**：`iv_config_open(dir,name)` → 读 `<dir>/<name>.json` → json-c 解析 → 递归展平成"点分键 → 定长条目" → 与内置默认值表比对补齐 → 句柄返回。取值走 `item_find()` 线性查表（键数上限 32，不值得上哈希）；改值只改内存条目并置 `dirty`；`iv_config_save()` 才整体校验 + 原子落盘。
- **关键数据结构**：`cfg_item_t`（键 + 类型 + 来源 + 联合值）、`struct iv_config`（静态池 4 槽，含路径/inotify fd/订阅者表）、`cfg_snapshot_t`（事务式重载用的整份内存快照）。
- **文件格式**：`{"_meta":{"schema","version","crc"}, 业务键按点分键嵌套在最外层}`。元数据收进 `_meta`、业务键在顶层、`_` 前缀留给元数据（`set_*` 亦拒绝），三者不会撞名。`version` 每次成功保存 +1；`crc` 是全部业务键按 key 排序后 `key=type:value\n` 指纹串的 CRC-16/MODBUS。
- **八个功能的落点**：F1 `iv_config_open()`；F2 `iv_config_get_str/int/bool` + `_origin()`；F3 `iv_config_set_*` + `_save()`；F4 内置默认值表（14 项）+ `fill_missing_defaults()` + `_fill_defaults()`；F5 `iv_config_save()` 内 tmp → `fsync` → `rename` → `fsync(dir)`；F6 `_watch_fd()` / `_watch_poll()`（inotify 监听**目录**）；F7 `_subscribe()`（校验全过才替换内存再逐个通知）；F8 `_secure_read()`。
- **校验四类**：① 类型（默认值表钉死已知键类型；**另新增**"占着已知键父路径的标量键判非法"）；② 范围（整数闭区间）；③ 引用（本步无适用项，密钥走 F8 独立接口）；④ 跨字段（探活超时 < 探活间隔；双 WAN 主备网卡不得同名）。任一类失败 ⇒ 保存返回 `IV_EINVAL`、`detail` 带错键名与原因、一个字段都不落盘。

### 解决什么问题

- 此前 `ivsboxd` 没有任何配置来源：参数只能硬编码或编译期注入。本步之后运行参数可从 `/mnt/UDISK/ivsbox/config/` 读、可写回、可在不重启的前提下随文件变化生效。
- **`crc` 不符只告警不拒绝**：手工编辑（正是 F6 的典型路径）必然让 `crc` 过期；若"校验不过就拒绝加载"，等于把"改配置"变成"停服"。因此 `crc` 只用于发现损坏与提醒，下次 `save()` 自动刷新。
- **启动期与运行期对"非法值"的处置刻意不同**：`open()` 逐键回退默认并计入 `invalid`（此时没有"旧配置"可留，必须照常启动 —— F4）；`watch_poll()` 只要出现任一非法值或解析失败就**整份拒绝**、旧值一字不动、一个订阅者都不通知（半新半旧比全旧更危险 —— F6/F7）。
- **实现过程中自行发现并修掉的 5 个缺陷**（写完即逐行复核时抓到，未流出到提交），其中两个是真功能缺陷：
  1. **热更新会把配置静默清空（F6 真违反）**：文件写成 `{"net": 5}`（子树写成标量）时，默认表补不进去、又不存在"非法值"，于是整份被当成合法配置接受 ⇒ `net.*` 全丢。修法：新增 `is_default_parent()`，凡占着已知键父路径的标量键一律判非法并剔除，随后默认子树正常补齐；热更新侧也因 `invalid>0` 而拒绝。
  2. **`iv_config_secure_read()` 静默截断**：缓冲放不下时截断后返回 `IV_OK`，会给出一个"看起来合法、实际错误"的令牌。修法：读满 `cap-1` 后再探一字节，能读到即 `IV_ERANGE`。
  3. 头文件注释块被 `set_*/save()` 里的 `*/` 提前闭合 → 整份头文件解析错乱、报一串"unused parameter"假错。修法：改写该句避开 `*/`。
  4. `iv_config_open()` 里一段死代码 + `.tmp` 路径用 `snprintf` 拼装会断 `-Wformat-truncation/-Werror` 编译。修法：删死代码、改有界 `memcpy` 手工拼装。
  5. `-Werror=empty-body`（`else if (...) ;`）。修法：该分支本就冗余，删除。
- **另修正两处文档与实现不符**：头文件把文件结构写成 `schema/version/crc/data` 扁平四键（实现是 `_meta` + 顶层业务键）；`iv_config_fill_defaults()` 声称"写盘失败不修改内存"（实现是先补齐内存再 save）。均改为与实现一致。

### 影响范围

- **新增依赖**：`libivmodules.a` 现在依赖 `json-c`。`-ljson-c` 只加在**最终可执行**的链接行（两端 `mk/toolchain-*.mk` 的 `$(LDLIBS)`，已在 `b289884` 就位），`libivcore` / `libivhal` 里没有 json-c 符号，依赖方向未被破坏。
- **板端是硬动态依赖**：sysroot 只有 `libjson-c.so`（没有 `.a`）⇒ ARM 产物运行时需要 rootfs 的 `libjson-c.so.4`。**该库不可从 rootfs 移除**。
- **`IV_CFG_DIR_DEFAULT`＝`/mnt/UDISK/ivsbox/config`**：依赖 `/mnt/UDISK` 已挂载 ⇒ **S10 的 init 脚本编号必须 > 60**（`S65ivsboxd`），否则会写进 rootfs 上的同名空目录。`open()` 会按需 `mkdir` 该目录（F4 要求"文件不存在也照常启动"，补完默认要有地方落盘）。
- **单线程契约**：本模块所有接口（含只读的 `get_*`）只在 reactor 线程内调用，与 `iv_reactor` 同一条纪律 —— 内部无锁，`watch_fd()` 返回的 inotify fd 归本模块所有（随 `close()` 关闭），调用方**只注册、不关闭**。

## 2026-09-30 08:51 M1-S9 SQLite 封装

### 干了什么事

- **新增三个文件**：
  - `include/ivsbox/iv_db.h`：对外接口。不暴露 `sqlite3` 类型（句柄不透明），只提供 `iv_db_open/close/exec/scalar_int/check_integrity` 与 `iv_db_begin/commit/rollback` 宏。
  - `src/core/iv_db.c`：实现，进 `libivcore.a`。封装 `sqlite3_open_v2`：自动建库目录、启用 WAL、设置 busy_timeout；打开前校验文件 header 魔数，非法则重命名为 `*.corrupt` 并重建；若 SQLite 自身报 `SQLITE_CORRUPT/NOTADB` 再走一遍同样恢复。
  - `tests/unit/test_db.c`：6 组用例覆盖 open 自动建目录、建表/插入/整型标量、事务回滚、WAL 文件生成、损坏库恢复、integrity_check、非法输入。
- **构建**：`mk/toolchain-host.mk` 与 `mk/toolchain-tina-arm.mk` 的 `LDLIBS` 追加 `-lsqlite3`。
- **关键数据流**：`iv_db_open(path, &db)` → `mkdir_p` 建目录 → `header_valid` 预检 → `sqlite3_open_v2` → `busy_timeout` → `PRAGMA journal_mode=WAL`；`iv_db_exec` 直接调用 `sqlite3_exec`；`iv_db_scalar_int` 用 `prepare/step/finalize` 取首行首列整数；`iv_db_check_integrity` 执行 `PRAGMA integrity_check` 并比对结果是否为 `"ok"`。
- **损坏恢复**：预检发现文件存在但 header 不是 `"SQLite format 3\0"`，或 `sqlite3_open_v2` 返回 `SQLITE_CORRUPT/NOTADB` 时，把原文件移到 `path.corrupt`，然后以 `CREATE` 方式重新打开，得到干净新库。

### 解决什么问题

- 此前项目没有持久化结构化存储能力，后续档案/审计/网络历史没有落点。S9 提供一个主控独占、位于 `/mnt/UDISK/ivsbox/db/control.db` 的 SQLite 底座。
- 坏库不直接覆盖：把损坏文件保留为 `.corrupt`，便于人工/脚本事后分析，同时让服务能继续启动。
- WAL + busy_timeout 让单写者模型下并发读尽可能不被阻塞，也避免瞬时锁竞争导致写失败。

### 影响范围

  1. 复杂查询（多列/多行/BLOB）未封装，需要时调用方自行 include `<sqlite3.h>`，但建议只读场景使用。

- **open 流程**：`open(O_RDWR|O_NOCTTY|O_NONBLOCK|O_CLOEXEC)` → `flock(LOCK_EX|LOCK_NB)` → `isatty()` 校验 → `cfmakeraw` → 清 `CRTSCTS`／置 `CLOCAL|CREAD`／按 cfg 设 `CSIZE`、`PARENB|PARODD`、`CSTOPB`、`VMIN=0`、`VTIME=0` → `cfsetispeed/cfsetospeed` → `tcsetattr(TCSANOW)` → `tcflush(TCIOFLUSH)`。顺序不能换：`cfmakeraw` 会把 `CSIZE` 一起清掉。
- **两个语义要点**：① `read` 把 `read()==0` 翻译成 `IV_EAGAIN`（`VMIN=0` 下 0 表示"当前没数据"，**不是 EOF** —— 串口没有"连接"概念，误判成断链会很难查）；② `write` 是**字节流**语义，返回**实际写入字节数**（可能小于请求长度，调用方续写），与 `iv_chan_send()` 的整包语义刻意不同。
- **单实例锁口径变更**：计划原写 `flock(/var/run/ivsbox/serial.lock)`，实现改为 **`flock(串口 fd, LOCK_EX|LOCK_NB)`**（少一个路径依赖；锁随 fd 关闭/进程退出由内核自动释放；`fuser /dev/ttySAC<n>` 同样可诊断）。语义不变：同路径第二次打开一律 `IV_EBUSY`（含同进程重复打开），close 后可再开。计划 §S2.1 已回写。

### 解决什么问题

- M2 的第一步此前是空的 —— 板上没有任何代码能把串口**打开并配成 raw**；S2.2 帧解析器、S2.3 可靠层都建立在它之上。现在有了。

## 2026-10-08 15:58 修正帧长度域字节序（大端→小端，依据单片机现网源码）＋协议事实沉淀

### 干了什么事

- **修正 `ivsbox/src/modules/link/iv_frame.c` 的字节序**（本次核心）：
  - 解析：`ST_LEN_H` 由 `need = b << 8` 改为 `need = b`（低字节）；`ST_LEN_L` 由 `need |= b` 改为 `need |= b << 8`（高字节）。

- **`ivsbox/include/ivsbox/iv_frame.h`**：帧规格注释里"len 大端（推断项）"更正为"**小端**"，并附源码出处。
- **两个单测的手工组帧 `mk()`**（`test_frame.c` / `test_link.c`）同步改小端；`test_frame.c` 的 0F 洪流用例、`test_link.c` 的"坏帧不置 UP"用例按小端重算/重写（详见"解决什么问题"）。

### 解决什么问题

- **真 bug（会导致全部真实联调失败）**：S2.2 起初按"大端"推断长度域并据此实现，而单片机现网是小端（`com.c`：发送 `data[3]=data_len; data[4]=data_len>>8;`；接收 `size = rec_buff[3] | (rec_buff[4] << 8)`）。**凡 len≠0 的帧都会编/解错** —— 而且是"能跑起来但数据全错"的隐性错误，单测（两端都是本工程）发现不了，只有真实联调或核对对端源码才暴露。
- **测试同源风险**：单测用**独立手工组帧**与 `iv_frame_build()` 对比，本意是防"实现与测试同错互相掩盖"，但手工组帧本身也是本工程写的 —— 它同样按大端，于是**两边一起错、测试仍全绿**。教训：跨端协议的字节序，**测试自证不能替代对端源码确认**。本次两边同时改。
- **测试自身的两处修正（小端暴露）**：① 0F 洪流用例：状态机按"每 5 字节一帧"切出 `len=0x0F0F` 的超长候选帧，64 B → 12 次 `too_long`，残留半截帧由 `tick()` 复位兜底；② `test_link` 坏帧用例：原**手写 8 字节**在小端下 `len` 被解析为 256，成了一个**合法的"等待更多数据"帧**而非坏帧（暴露了手写字节的脆弱），改为"用 `mk()` 组正常帧、再打坏其 CRC 字节"。
- **协议事实沉淀**：JSON schema（0xE1 应答键表、0xC2 事件 TAG 表、0xF1 应答键、0xD1 请求 JSON）写入 §18.2，为 S2.6 字段级对接提供依据。
