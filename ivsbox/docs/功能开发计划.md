## 0. 通用规则（贯穿所有阶段）

- **开发闭环**：编译 VM（192.168.2.115，用户 `user`）交叉编译（`arm-linux-gnueabi-` + `-D_GNU_SOURCE`）→ `pscp` 上板（192.168.2.112 `/tmp`）→ `plink` 执行 + COM4 串口观察。
- **代码约束**：C11；`core` 不依赖 HAL，能在 Host 跑单测；模块间禁止修改对方私有数据；依赖方向 `libivcore`(仅 libc) → `libivhal` → `libivmodules` → `ivsboxd`，靠链接顺序写死。
- **构建口径**：**只用 GNU Make**（架构文档 §15）。顶层 `Makefile` 唯一入口 + `mk/` include 片段；裸 `make` ＝ Host Debug，`make arm` ＝ 板端产物；`make test` / `make asan` 驱动测试。
- **选型纪律**：优先现成 Linux 库 → 没有再自研 → 自研时登记"待安装库清单"，做镜像时替换。
- **每步收尾四件事**：本文档 §0.1 追加一行 → 登记 `docs/修改记录.md` → git 提交推送 → 清理临时文件。工具层规则见根目录 `AGENTS.md`。
- **接口冻结依赖**（架构 §18 共 9 项）：相关步骤标注了前置项；未冻结前该步只做到"模拟器可验证"层级，不对真实对端联调。
- **载荷/配置格式口径**：按架构文档现行口径用 JSON（§5.1/§10.2）。**M1-S7 已决定通道层不解析载荷**（载荷对通道是 `void *` + `len`），故 JSON 库选型推迟到真正需要它的那一步。**2026-09-29 用户拍板：JSON 库＝`json-c`**（板端与 ARM sysroot 均已自带，不必自制镜像、也不必登记待安装库）。当日实测平台事实：板端 rootfs 与 sysroot 均为 **json-c 0.13.1 / SONAME `libjson-c.so.4`**，且 sysroot **只有 `.so`、没有 `libjson-c.a`** ⇒ 板端二进制对它**动态依赖**（运行时由 rootfs 的 `libjson-c.so.4` 提供）；编译 VM 宿主为 **0.15 / `libjson-c.so.5`**。由此产生三条硬约束：① **代码只准用 0.13 的 API 子集**（以 sysroot 头文件为准；宿主 0.15 头文件里新增的接口一律不能用，否则 host 绿、板端链接失败）；② `libivcore` 纪律是「仅 libc」，**json-c 符号不得出现在 core**，配置模块落 `src/modules/config/`，`-ljson-c` 只加在**最终可执行**的链接行；③ 架构 §15.5 依赖表里 `libivcore` 一行的「配置」按「配置值的内存模型／访问（仅 libc），不含 JSON 解析」解读、解析归 `src/modules/config/` —— **该解读已于 2026-09-29 经用户裁定采纳，并已补进架构文档 §15.5**（同处写明：外部库落点＝`mk/toolchain-*.mk` 的 `$(LDLIBS)`，届时加 `-ljson-c`；`-ljson-c` 要等 S8 真正落地时与 `mk/` 一并加，文档不抢先于代码）。
- **数据根目录与守护方式口径（2026-09-29 定；依据＝板端实测 ＋ 姊妹工程 `bird` 现行做法）**：
  - **板端存储真相（2026-09-29 15:0x 起改为 eMMC 启动，此前「SD 启动」时期的读数全部作废）**：板上**同时有两个块设备** —— `mmcblk0`＝**焊死的 eMMC**（`device/type` = `MMC`、`device/name` = `SPeMMC`，用户区 15,147,008 扇区 ≈ **7.22 GiB**），`mmcblk1`＝**SD 卡**（`type` = `SD`、`name` = `SU32G` ≈ 29.7 GiB，仍在槽里，当前只自动挂了 `mmcblk1p1`（声明 128 MiB vfat）到 `/run/media/mmcblk1p1`）。`root=/dev/mmcblk0p5`（rootfs，2.0 GiB ext4，实测可用 1.5 GiB）。
  - **⚠ 内核 mmc 编号已变**：SD 启动时期 `mmcblk0` 是 SD 卡；eMMC 启动后 `mmcblk0` 是 eMMC、`mmcblk1` 才是 SD 卡 ⇒ **凡按 `/dev/mmcblk0` 硬编码的旧假设一律作废**，改用 `/dev/by-name/<分区名>`（开机由 `/etc/init.d/S60mount_udisk` → `/etc/partition_op.sh` 的 `do_device_node_switch()` 依 `/proc/cmdline` 现建；实测已存在：`UDISK→p10`、`rootfs→p5`、`private→p8`、`boot→p4`、`recovery→p9` …）。
  - **⇒ 落点＝eMMC 的 `UDISK` 分区**（`/dev/by-name/UDISK` = `/dev/mmcblk0p10`，**≈5.05 GiB** ext4，开机自动挂到 **`/mnt/UDISK`**，实测可用 4.7 GiB）。它是板上**唯一「焊死、不可拔、可写、开机自动挂载」的数据分区**，正好满足架构 §10.3「数据库位于内部可靠数据分区，不直接放在可拔出的 SD 卡」。**本工程取独立命名空间 `/mnt/UDISK/ivsbox/`**：`config/`、`db/`、`queue/`、`ota/`、`releases/`、`secure/`、`current`/`previous`；**日志单独落 `/mnt/UDISK/log/`**（沿用 `iv_log` 既有「独立 `log` 根目录 ＋ `<YYYY-MM-DD>/<HH>.log`」结构，也与板上既有 `/mnt/UDISK/log/` 同级）。
  - **为什么不落 rootfs 的 `/opt`**：rootfs 只有 2.0 GiB、可用 1.5 GiB，装不下 OTA 的双版本应用；且 rootfs 随固件重刷即丢。
  - **2026-09-29 用户口径变更（覆盖旧约束）**：旧约束「`/mnt/UDISK` 只放视频文件与抓拍图片，不得存放任何其他东西」**已作废** —— 那条写在「UDISK 是 SD 卡的 27.5 GiB 分区」的前提上；eMMC 启动后 `UDISK` 变成 eMMC 的 5.05 GiB 分区，SD 那个 27.5 GiB 分区（`/dev/mmcblk1p10`）**根本没挂载**。**用户明确：日志存储位置改到 `/mnt/UDISK`** ⇒ 配置 / DB / 队列 / OTA / 日志一律落 UDISK 命名空间。**媒体文件仍归 SD 卡**（大容量、可拔换），但 SD 数据分区当前未挂载，挂载点**待确认**（架构 §10.1 现写 `/mnt/media/ivsbox/`；姊妹工程 `bird` 用 `/mnt/sdcard`）。
  - **⚠ 启动时序约束（新，必须遵守）**：`/mnt/UDISK` 由 `S60mount_udisk` 挂载，而 `rcS` 只按编号顺序执行 `/etc/init.d/S??*` ⇒ **应用的 init 脚本编号必须 > 60**（§S10 原写的 `S50ivsboxd` **作废**，改 **`S65ivsboxd`**）。否则 UDISK 未挂载就启动，日志/配置会写进 rootfs 上的同名空目录（重启即丢、还白占 rootfs）。
  - **⚠ UDISK 可能被开机脚本格式化（存量风险，必须记住）**：`S60mount_udisk` 先 `do_format_filesystem /dev/by-name/UDISK ext4`，其实现是「先试 `mount -t ext4`，**挂不上就 `mkfs.ext4`**」⇒ 分区损坏导致挂载失败时，脚本会**直接重建文件系统、静默清空全部数据**。另挂载参数为 `-o rw,async`（非 sync）⇒ 关键写入必须自己 `fsync`。**这两条是 §S7.2「升级前备份 → 升级后恢复」的直接动因。** 另：**按整片重刷 eMMC（含 GPT／全部分区）会连 UDISK 一起清**；只重刷 rootfs 分区是否保留 UDISK，**需按实际刷机方式确认** —— 保数据策略仍待用户拍板。
  - **工厂身份不走文件系统**：写在 eMMC 的 **`private` 裸分区**（`/dev/by-name/private` = `/dev/mmcblk0p8`，16 MiB，实测当前**全 0、未格式化、未挂载**），定长二进制 ＋ 校验，出厂一次写入后置锁定位只读；**不落 UDISK**（避免被上面的格式化风险牵连）。见 §S5.5。
  - **配置的存储方式照 `bird` 口径**：单文件 JSON（`bird` 用 `/opt/config/config.json`，读写走 Go 标准库 `encoding/json`），**写盘一律原子替换** —— `bird` 的 `atomicWriteFile()` 实现是「写 `path + ".tmp"` → `f.Sync()` → `f.Close()` → `os.Rename(tmp, path)`」（`internal/config/config_loader.go`），与本计划 §S8 第 2 条要求的「tmp → fsync → rename」**逐条同构**，属跨语言可直接对齐的成熟做法。配置优先级也照它：**本地文件 → 远程下发 → 内置默认值**（`config_manager.go` 的 `LoadConfig()`）；校验失败或字段缺失时**就地补默认值**而非整份拒绝（`validator.go`）。
  - **守护方式**：板端是**经典 sysvinit**，**没有 procd**（`/sbin/procd`、`/usr/sbin/procd`、`/etc/rc.common` 全不存在）、没有 systemd、**没有 `/etc/rc.local`**；`/etc/inittab` 只 `respawn` 控制台 shell，开机流程为 `rc_embedsky.S` / `rc_daemon.S` / `rcS` → 逐个执行 `/etc/init.d/S??*`。板端**有 `/sbin/start-stop-daemon`**（Buildroot 原生做法），BusyBox **v1.33.2**。**参照姊妹工程 `bird` 的成熟做法**（`code/bird/scripts/`）：`/etc/init.d/` 里的启动脚本（开机拉起）→ `start_bird.sh` → 后台 `monitor.sh &`，**每 5 秒轮询** `ps -o comm | grep -x bird`，进程没了就重新拉起（它同时守护 `bird` / `media` / `frpc`，并每 10 分钟检查一次 4G 链路）。本工程照此实现，见 §S10。**§S10 原写的 `USE_PROCD=1` / `procd_set_param` 在板上跑不起来，已作废。**

### S3 CRC

- **实现什么**：帧校验基础件。
- **怎么实现**（`src/core/iv_crc.c` + `include/ivsbox/iv_crc.h`）：**逐字节按位实现——零依赖、不查表、不引 zlib**（2026-09-28 据现网实测改口径，原"zlib `crc32` 薄包装 + `-lz`"作废：zlib 的 crc32 是 CRC-32，与现网两者都不相干）。只做现网**实际在用**的两种，参数与单片机工程 `General_Version/main/Middlewares/tool/src/crc.c` 严格对齐：
  - `iv_crc8()`：**CRC-8/SMBUS**（poly `0x07`、init `0x00`、不反射、xorout `0x00`）
  - `iv_crc16_modbus()`：**CRC-16/MODBUS**（poly `0x8005`→反射形式 `0xA001`、init `0xFFFF`、反射、xorout `0x0000`）
  两者都带 `seed` 参数以支持分段累计（`xorout=0` 且无最终反射，故把上一段返回值直接当 seed 传入即可）。不实现 CRC-32（现网无此需求）。依据：该固件的链接器 map 显示 `usMBCRC16`、`usSumFunction` 均未被引用已被剔除，真正在跑的只有 `calc_crc8`（UART 帧）与 `CRC16_MODBUS`（OTA 包）。
- **怎么验证**：`tests/unit/test_crc.c`——标准向量（`"123456789"` → CRC8 **`0xF4`** / CRC16 **`0x4B37`**）、空串与 NULL、**由 MCU 现网实现算出的 21 组长度扫描黄金表**（数据 `buf[i]=i&0xFF`，钉死跨端一致）、字符串与短帧向量、分段累计（二段 0..64 全切分点 + 三段）与一次算完等价、1024 字节长缓冲；板端对同一输入输出与 Host 一致（交叉验证）。

### S4 Reactor（epoll 事件循环）

- **实现什么**：`ivsboxd` 的单线程事件核心，一切 fd 事件的分发中心。
- **怎么实现**（`src/core/iv_reactor.c` + `include/ivsbox/iv_reactor.h`；**本节口径 2026-09-28 14:31 按实现落地结果重写**）：
  1. `iv_event_t`：fd、注册事件位、回调、`arg`、`active`（1＝已注册，0＝已注销）；`iv_reactor_t`：epoll fd、`epoll_wait` 输出数组、timerfd、signalfd、进度号、运行标志、活性事件链表、待回收（zombie）链表、定时器最小堆。
  2. 接口：`iv_reactor_create(max_events)` / `destroy` / `run` / `stop` / `progress` / `timer_count`；`iv_reactor_add(r,fd,events,cb,arg) -> iv_event_t*`（**返回句柄**，失败返 NULL）/ `mod(r,ev,events)` / `del(r,ev)`；`iv_timer_add(r,timeout_ms,cb,arg) -> iv_timer_t*` / `iv_timer_cancel`。
     - **口径变更**：原"`add` 只回错误码、`del(reactor,fd)` 以 fd 为键"作废——`epoll_event.data.ptr` 里存的是句柄指针，以 fd 为键会逼出一张多余的 fd→event 索引表。改为句柄语义后 `del` 不再需要 fd 查找。
     - 事件位用自有命名空间（`IV_EV_READ/WRITE/ONESHOT`，回调可见 `IV_EV_ERR/HUP/RDHUP`），调用方**不再包含 `<sys/epoll.h>`**；注册 `IV_EV_READ` 时自动附加 `EPOLLRDHUP`，`ERR/HUP` 由 epoll 无条件上报、必须翻译后交给回调。
  3. 定时器：最小堆存**绝对到期时刻**（`clock_gettime(CLOCK_MONOTONIC)` 毫秒），一个 `timerfd` 作唤醒闹钟（必须读干，否则电平触发反复上报），到期后**弹空所有 `deadline <= now`** 的节点逐个回调（只处理堆顶一个是典型 bug）。定时器为**一次性语义**，周期触发在回调里重新 `add`。取消采用**惰性标记**：只置 `canceled` 不立即释放（节点还在堆里，提前 free 即成悬空指针），由"到期弹出"或"批次末尾压缩"回收；回调里取消自己同样安全。上限 `IV_REACTOR_TIMER_MAX`(256)，满则 `add` 返 NULL，不扩容不排队。
  4. 时间基准**不得调用 `iv_clock_monotonic_ms()`**：`iv_clock` 属 `libivhal`，而链接顺序 `-livmodules -livhal -livcore` 把 core 排在最后，core 反向引用会**当场链接失败**（`-Wl,--no-undefined`）。本模块直接调 libc `clock_gettime`，既满足"libivcore 仅 libc"，也不改任何链接配置。
  5. 信号：`sigprocmask`（**不是** `pthread_sigmask`——后者在板端 glibc 2.25 位于 libpthread，会把 `-lpthread` 引进 libivcore）屏蔽 SIGTERM/SIGINT/SIGPIPE 后建 `signalfd` 纳入分发；必须在建任何线程之前调用（线程掩码创建时继承）。SIGTERM/SIGINT 只清 `running` 让 `run` 自然返回，不得在回调里 destroy。
  6. 进度号：`volatile uint32_t`，**每轮循环（含超时返回的空轮）递增 1**，放在错误分支之前（EINTR 同样算前进）。**刻意不用 64 位**：armv7 上对齐的 32 位读写天然原子，64 位会被拆成两条指令产生撕裂值，`_Atomic uint64_t` 又会引入 `-latomic`。读侧必须用差值 `(uint32_t)(now-last) != 0`，不能写 `now > last`（49 天回绕）。
  7. `epoll_wait` 超时 = `min(1000ms, 堆顶剩余)`，**禁止用 -1**：空闲期进度号不推进会被 S6 误判为主循环卡死。EINTR 不算错误，继续等待。
  8. fd 所有权：`destroy` 只关自己创建的 epoll/timerfd/signalfd 并恢复信号掩码，**不关调用方注册的 fd**；所有自身 fd 一律 `*_CLOEXEC`（S10 下防止泄漏到子进程）。
  9. 并发：除 `iv_reactor_progress()` 只读外**全部接口只在 reactor 线程内调用**，内部无锁；S5 的 worker 必须经 eventfd 回传后再在主循环里处理。
  10. 单次回调约束（§4.2，本层不提供强制手段）：只做解析、状态更新、分发；禁止 DNS、同步 SNMP/ONVIF、长文件 IO（走 S5 慢任务池）。
- **怎么验证**：`tests/unit/test_reactor.c` 8 组用例——入参校验与重复 `add`/`ONESHOT-only` 拒绝、定时器上限拒绝、eventfd 自触发与 `del` 后不再回调、**同一批内 `del` 另一个事件**（延迟释放路径，真正判据是 `make asan` 无 use-after-free）、三个同刻到期全部触发、取消后不触发（含重复取消返 `IV_ENOENT`）、回调里自取消、回调里重挂 5 次、**空闲轮进度号仍递增**、SIGTERM 从回调内投递后 `run` 以 `IV_OK` 返回且后续定时器不执行、**EINTR 后主循环继续**。`make test` 7/7、`make asan` 全绿零错。**板端验证改用 ARM 版单测本身**（而非原计划的"挂 timerfd 的最小 main"）：ARM `test_reactor` 在 192.168.2.112 上直接跑，输出与 Host 逐字一致 —— 它已经把 epoll/timerfd/signalfd/eventfd 全在真实内核与 glibc 上跑了一遍，比最小 main 覆盖更全，且不需要往 `src/app/main.c` 里塞临时代码（规则 6）。

### S5 慢任务池

- **实现什么**：固定 2 worker 的有界槽位池，承接一切不可控阻塞操作。
- **怎么实现**（`src/modules/iv_taskpool.c` + `include/ivsbox/iv_taskpool.h`；**本节口径 2026-09-28 15:40 按实现落地结果重写**）：
  1. **落点变更（重要）**：计划原写 `src/core/iv_taskpool.c/.h`，实现时改为 **`src/modules/`**。原因是本模块必须用 pthread，而 `libivcore` 的纪律是「仅 libc」—— S4 的 `iv_reactor` 正是靠 `sigprocmask` 替掉 `pthread_sigmask` 才守住那条纪律的。放进 modules 后架构 §15.5 依赖方向表不变，且本模块可直接调 `iv_clock_monotonic_ms()`（libivhal）。代价是链接期必须给 `-lpthread`，已加进两端 `mk/toolchain-*.mk` 的 `LDLIBS`（**板端不能省**：glibc 2.25 的 pthread 在独立 libpthread 里；VM 的新 glibc 不加也能过，属"VM 绿、板端挂"陷阱）。
  2. **槽位式队列，不用紧凑环形缓冲**：定长槽位数组 + 每槽状态 `FREE/QUEUED/RUNNING/DONE/DISPATCHING`。取消能在 O(n) 内找到任意在飞任务（n ≤ 64）；紧凑队列一旦元素被 worker 取走就脱离可见范围，`cancel` 会找不到正在执行的任务、只能返回 ENOENT，那是错的。
  3. **完成的任务不立即释放槽位**：停在 DONE 等 `iv_taskpool_process()` 取走。省掉一份结果拷贝；且调用方若忘了挂 eventfd / 忘调 `process`，表现为槽位耗尽后 submit 一律 `IV_EBUSY` —— 有界失败，不泄漏不崩溃，问题立刻可见。
  4. **并发口径**：队列锁 + cond（**绑 `CLOCK_MONOTONIC`**，`pthread_condattr_setclock`；默认的 `CLOCK_REALTIME` 会被 S2.5 的 GPS 对时跳变打乱）；`submit` 用 `cond_broadcast`（两 worker 都空闲时多次 `signal` 可能落到同一线程，第二个任务要白等 1s）；`process` 的 `on_done` **在锁外调用**，回调里再 `submit`/`cancel` 不死锁；`process(max)` 限流时**若处理完 max 条仍有 DONE 残留，会补写一次 eventfd 自唤醒**（eventfd 在处理前已被读干，不补这一下残留槽位就要等到下一个任务完成才有唤醒源，之后若没新任务就永远占着，直到 destroy）。
  5. **取消是协作式的**：QUEUED 直接释放槽位、回调不执行；RUNNING 只置标志、不打断执行，任务函数自行退出后回调仍执行（rc 通常 `IV_ECANCELED`）。任务函数用头文件提供的 `iv_task_canceled(ctx)` 检查（原子读）。
     - **`destroy()` 走同一条路径**（2026-09-28 17:33 补）：置停止标志的同时对全部 RUNNING 槽置 `cancel=1`，再 join —— 即本步**原口径"destroy 先置取消标志再 join"**，首版实现漏了这一步（只做了 `stopping=1 + broadcast + join`）。不补的话，S10 的关机/重启路径撞上一个 30s 的 SNMP 超时任务就要干等 30s，守护脚本的重启窗口未必等得起。任务函数完全不检查标志时 destroy 仍会等它跑完（协作式的固有边界）。
  6. **截止时间是"开工准入"**：worker 取出任务时若已过期就不执行、直接以 `IV_ETIMEDOUT` 完成；正在跑的任务绝不打断。
  7. **空闲轮同样推进进度号**：worker 用 `pthread_cond_timedwait` 带 1s 超时，超时也 `progress++`。与 S4 的 `epoll_wait` 有限超时同一条口径 —— 不这样做，S6 会把"两个 worker 都闲着"误判成"worker 死锁"并停喂看门狗。
  8. **信号掩码由本模块自己阻塞**（`pthread_sigmask`，建线程之前，不恢复）：装配顺序是 taskpool 先、Reactor 后，而 `iv_reactor_create()` 又要求"必须在建任何线程之前"阻塞信号 —— 两个要求直接冲突，由"创建线程的人"负责之后无论先后都正确。
  9. **两处跨线程量走 `__atomic_*` + relaxed**：worker 进度号、任务 cancel 标志。它们没有锁提供 happens-before，裸读写会被 ThreadSanitizer 判成数据竞争。S4 的 `iv_reactor_progress` 用 `volatile` 表达"别人会改"（当时不过 TSan），本模块要过 TSan 故升级为真原子访问；armv5/armv7 上 4 字节 relaxed 是单条 `ldr`，不引 libatomic（`--no-undefined` 已验证）。
- **怎么验证**（`tests/unit/test_taskpool.c`，15 组用例）：入参校验与 create 参数夹取；正常完成 + 结果内容逐条核对；队列满恰好一个 `IV_EBUSY` 且 `pending` 饱和在队列容量；取消 QUEUED（回调不执行）/ 取消 RUNNING（`iv_task_canceled` 被观察到、回调仍执行、rc = `IV_ECANCELED`）/ 取消不存在与重复取消均 `IV_ENOENT`；排队放到过期则任务体不执行、rc = `IV_ETIMEDOUT`；空闲 1.2s 后进度号仍递增；`process(max)` 限流 2/2/1；**限流后仍有 DONE 残留时 eventfd 被补写自唤醒**；`on_done` 里再 submit 不死锁；队列非空时 destroy 直接返回；**destroy 对正在执行的 2s 长任务置取消标志并迅速返回（< 1s）**；200 轮 create/destroy 后 `/proc/self/fd` 数量不变；**与 Reactor 联调** —— 3 个 120ms 慢任务运行期间 tick 定时器多次触发、主循环进度号持续推进（Reactor 未被阻塞，正是 S6 判活要的结论）。
  - `make test` 8/8、`make asan` 8/8 零错、**新增的 `make tsan` 8/8 零警告**、新增两文件 `-fanalyzer` 零报告。
  - **TSan 在 VM 上必须用 `setarch -R` 运行**（或调低 `vm.mmap_rnd_bits`）：Ubuntu 22.04 内核的 ASLR 熵与 gcc 11 的 TSan 冲突，直接跑会 `FATAL: ThreadSanitizer: unexpected memory mapping`。这是**环境问题不是代码问题**。
  - **板端验证沿用 S4 的做法**：ARM 版 `test_taskpool` 直接在 192.168.2.112 上跑，输出与 Host 逐字一致 —— 它把 pthread/cond/eventfd 在真实内核 + glibc 2.25 上跑了一遍。

### S6 健康线程 + 看门狗门控

- **实现什么**：独立健康线程 + 看门狗门控。只有"主循环在走 **且** 慢任务池没死锁"才喂 `/dev/watchdog`；任一超预算就停喂，由整机复位兜底。
- **怎么实现**（`src/hardware/iv_watchdog.c` + `src/modules/iv_health.c`）：
  1. **两层分工**：
     - `iv_watchdog`（**libivhal**，`include/ivsbox/iv_watchdog.h`）：只做 `open / set_timeout / get_timeout / keepalive / disable / close` 六个 syscall 薄包装（2026-09-29 新增后两个：`get_timeout` 供启动自检读回实际超时，`disable` 供正常停机写 `'V'` 停狗），**不含判定逻辑、不引入 pthread**。除 `open()` 外全部接口收 fd，因此宿主/VM 上用一对 pipe 就能单测，不需要任何测试专用钩子。
     - `iv_health`（**libivmodules**，`include/ivsbox/iv_health.h`）：独立 pthread，负责判据与喂狗/停喂。
     - **落点与本节原文不同**：原文写 `src/app/health.c`，已更正为 **`src/modules/iv_health.c`**。原因：app 层的 `.c` 不参与任何静态库，放那里 `tests/unit/test_health.c` 链接不到符号（Makefile 只链三个 `.a`）。
  2. **判据 ＝ 进度号 ＋ 变化时刻两个量**：每个被观察对象维护「上次进度号」＋「该进度号最近一次变化的单调时刻」；进度号变了就刷新时刻，没变且 `now - 变化时刻 >= stuck_ms` 才判死；首次观察只播种、不判死。**只看进度号本身、或把进度号当时间戳用都是错的**（后者量纲错位，会让判据在不该报的时候恒定报死）。
     进度号来源：`iv_reactor_progress()`（S4 已埋）、`iv_taskpool_worker_progress(i)`（S5 已埋）。
  3. **`stuck_ms` 默认 10s、检查节奏 1s、看门狗超时 16s**，必须满足 `stuck_ms + interval_ms < watchdog timeout` —— 否则"判据还没得出故障结论、狗就已经咬了"，门控形同虚设。**2026-09-29 口径更正（原口径在 T113 上不可达）**：超时从 30s 改为 **16s**。依据：板端驱动是 sunxi-wdt，其 `WDT_MAX_TIMEOUT = 16`（设备树节点 `watchdog@20500A0` 的 `compatible = allwinner,sun6i-a31-wdt` 且**没有** timeout 属性；驱动内建、`CONFIG_WATCHDOG_SYSFS` 未开），而内核 `watchdog_set_timeout()` 对越界请求是**直接 `-EINVAL` 拒绝、不做 clamp** —— 请求 30s 只会把窗口留在驱动默认的 16s，“显著大于判据窗口”与“给守护进程留重启窗口”两个理由同时落空。改为 16s 后“请求值＝实际值”，最坏结论时延 11s、余量 ~5s。该不变量已由 `src/modules/iv_health.c` 顶部的 `#if + #error` 在**编译期**钉死（换板子/换驱动改超时时会被当场拦下）。
     为什么"进度号 10s 不动"确实等价"卡死"：Reactor 的 `epoll_wait` 与 worker 的 `cond_timedwait` 都用有限超时、**空闲期也推进进度号** —— 这是 S4/S5 刻意埋下的前提。
     **2026-09-29 板端实测证实该超时值**：`GETTIMEOUT` 默认回读 `16`、`SETTIMEOUT(30)` 返回 `-1/EINVAL`、`SETTIMEOUT(16)` 返回 `0` ⇒ 「16s 在板上是真的、30s 确实不可达」由推断升级为实证。
  4. 判死后的动作：stderr 打一次最小现场（故障位＋进度号快照，**不依赖 `iv_log`**，避免"日志系统卡住"与"主循环卡住"互为因果时把最后一份证据也丢掉）→ `close(fd)` 停喂（**故意不写 `'V'`** —— 见第 6 条）→ 此后不再写。**不替主循环跑业务、不重启线程**。
  5. 健康线程不注册任何信号；装配顺序为 `iv_taskpool_create() → iv_reactor_create() → iv_health_start() → iv_reactor_run()`，保证它继承 taskpool 已经阻塞好的掩码。
     **2026-09-29 更正**：本节此前写的是 `（taskpool → health → reactor）`，**是错的、照做不可行** —— `iv_health_start()` 首参就是 reactor 指针，reactor 未建只能传 NULL，而 NULL 等于“不观察主循环”，会**静默废掉主循环判死**（没有事后 attach 接口），同时也违反 `iv_reactor_create()`“必须在创建任何线程之前调用”的要求。§S10 写的顺序本来就是对的，两节现已一致。
  6. **正常停机必须显式停狗**。`close()` 本身**不停狗**（2026-09-29 由内核 `watchdog_release()` 源码实证）：sunxi-wdt 声明了 `WDIOF_MAGICCLOSE`，内核只在“写过 magic 字符 `'V'`”或“驱动未声明 MAGICCLOSE”时才真正停；本工程 keepalive 固定写 `'\0'` ⇒ 判死时 close 之后内核补 1 次 ping 并打 `watchdog did not stop!`，狗继续倒计时、timeout 后整机复位（**这正是判死路径要的结果，判死路径绝不要写 `'V'`**）。反之，init 脚本的 `stop`／有序退出若只 close，狗仍在跑，约 16s 后必然把整机复位一次（脏复位）。为此新增两个薄包装：`iv_watchdog_disable(fd)`＝“写 `'V'` 再 close”，**只给正常停机路径用**；`iv_watchdog_get_timeout(fd)`＝读回内核记录的超时，供 S10 启动自检确认“实际超时 > stuck_ms + interval_ms”。另：`set_timeout(fd, 0)` **不是**“查询”（查询走独立的 `WDIOC_GETTIMEOUT`），已在入口按 `EINVAL` 拒绝。
     **2026-09-29 板端实测证实**：`GETSUPPORT` 回 `options=0x00008180`（含 `WDIOF_MAGICCLOSE`｜`WDIOF_KEEPALIVEPING`｜`WDIOF_SETTIMEOUT`）、`identity='sunxi-wdt'`；写 `'V'` 再 `close()` 后观察 20s（> 16s 超时）**整机未复位** ⇒ 正常停机路径有效；`/proc/config.gz` 亦确认 `CONFIG_WATCHDOG_NOWAYOUT` **未开**（若开则写 `'V'` 也停不了）。
  7. 跨线程量（`stopping`）走 `__atomic_*` + `memory_order_relaxed`（同 S5 纪律，裸读写会被 TSan 判成数据竞争）；快照走内部互斥锁，对外由 `iv_health_snapshot()` 加锁拷出。

### S7 本地通道：消息头 + UDS SEQPACKET 传输

- **实现什么**：`ivsboxd` 作为服务端的本地进程通道（帧头＋整包收发＋超时＋对端鉴权）。
  **通道层不理解载荷** —— 载荷对它是 `void *` + `len` 的一段不透明字节。
- **怎么实现**（`include/ivsbox/iv_chan.h` + `src/core/iv_chan.c`；**本节口径 2026-09-29 按实现落地结果重写**）：
  1. **改名**：原写 `iv_ipc.h` / `src/core/iv_ipc_srv.c` / `ivs_ipc_hdr_t` / `test_ipc.c`，2026-09-29 按用户要求全部改用 `chan`（`iv_chan.h` / `src/core/iv_chan.c` / `ivs_chan_hdr_t` / `test_chan.c`）。理由：安防语境中 `IPC` 指网络摄像机（IP Camera），与本项目 M4 对接对象重名。源文件名同时去掉 `_srv` 后缀 —— 本模块既有服务端也有连接端，`_srv` 会挡住后者。
  2. **消息头**（架构 §5.1）：`ivs_chan_hdr_t`，定长 **32 字节**。字段顺序与架构一致，**新增一个 `pad0` 显式填充**：原布局把 `uint64_t request_id` 放在偏移 12，靠编译器隐式填充到位；一旦换工具链/ABI 就可能静默错位，而错位的表现是"字段读到隔壁的值"这类最难查的故障。改为显式填充后布局由源码逐字节确定，并在头文件里用 `_Static_assert` 把 `sizeof` 与全部 `offsetof` **钉在编译期**。
  3. **不解析载荷（本步的关键决策）**：这样既守住 `libivcore`「仅 libc」的纪律（否则就要给 core 引入 JSON 库依赖，代价是整个依赖方向表），也让架构 §5.1 要求的第二种载荷（媒体高频状态的定长结构）有处可放。**连带效果：JSON 库选型从本步移除**（见 §0 第 16 条）。
  4. **不绑定事件循环**：模块不引用 `iv_reactor`，只提供 fd 级接口，由调用方把接听点 fd 与连接 fd 注册进自己的循环 —— 因为 `ivsbox-media` / `ivsbox-web` 是独立进程、各有控制循环；解绑后单测也能完全脱离 Reactor 运行。
  5. 传输：`socket(AF_UNIX, SOCK_SEQPACKET | SOCK_CLOEXEC | SOCK_NONBLOCK)`；默认路径 `/var/run/ivsbox/ctl`、权限 **0660**（`bind` 后显式 `chmod`，不让安全边界依赖进程 umask）。选 SEQPACKET 的理由是**内核保留消息边界**，一次 `recv` 必得一条完整消息，不必写半包/粘包状态机；选 `AF_UNIX` 而非回环 TCP 的理由是内核直给对端身份、文件权限限制谁能连、且可传文件描述符。
  6. **接听点的路径纪律**：已被**上一个 socket 文件**占用（进程被 kill 未清理）→ `unlink` 后重建，否则服务重启永远起不来；被**任何非 socket 的东西**占用 → 拒绝（`IV_EEXIST`）且**绝不删除该文件**；父目录不存在 → `IV_ENOENT`，**本模块不代建目录**（`/run` 是 tmpfs 755 root:root，普通用户建不了；目录由 init 脚本以 root 预建并 chown，见 §S10）。
  7. **鉴权两道门槛**：第一道是文件权限（非同属主/同组的进程在 `connect` 阶段就被内核挡掉）；第二道是 `SO_PEERCRED` 白名单（内核在连接建立瞬间记录，**对端伪造不了**）。白名单默认只放行 root 与接听点属主，**不写死任何 uid**（板端目前还没有 ivsbox 用户，放行谁留给装配时定）。被拒时**直接关闭连接、不发送任何回应**，不给扫描脚本当路标。
  8. **单包上限 64 KiB**（`IV_CHAN_MAX_PAYLOAD`）：这是架构 §5.1「单包最大长度固定」里的那个"固定"。实现用 `recv(..., MSG_TRUNC)` 一次拿到整包长度，超限即整包丢弃（SEQPACKET 语义自带，队列里不留残渣）。**图片/录像绝不许进载荷** —— 见架构 §5.1 的载荷三档口径。
  9. 超时：`iv_chan_recv_timeout()` 用 `poll` 实现；**拒绝负超时**（架构 §5.1 要求"请求必须设置超时"，不提供能睡死的接口）。**2026-09-29 11:14 修复轮**改为按 `CLOCK_MONOTONIC` 计**剩余预算**的循环：被信号打断（EINTR）时在**同一调用内**用剩余预算继续等，绝不把已花掉的时间丢掉重来 —— 否则持续信号流（SIGCHLD 之类）会把实际等待无限拉长，与上面这条纪律相悖；返回值中不再出现"因 EINTR 提前返回的 `IV_EAGAIN`"。发送用 `sendmsg` 两段 iovec 直接发出（不拼临时缓冲）、带 `MSG_NOSIGNAL` —— 但**该标志在本传输上是预防性的**：双端实测（VM 内核 6.8.0 / 板端 5.4.61-rt37）`AF_UNIX/SOCK_SEQPACKET` 上对端关闭后 `sendmsg` 只返回 `EPIPE`、**内核不送 SIGPIPE**，带不带该标志结果逐字相同（SIGPIPE 只在 `SOCK_STREAM` 上出现，同探针 rc=141）。全文件**零 malloc**：接收缓冲由调用方提供。
- **怎么验证**（已落地）
  - `tests/unit/test_chan.c`：① 布局锁定 —— `sizeof == 32`、8 个 `offsetof`、魔数的**内存字节序**恰为 `'I','V','S','B'`（只比数值不够，字节序反了跨端一样读不出）；② 头编解码与各失败路径；③ `socketpair` 上的正常往返、空载荷、超长被拒（**并验证紧跟其后的一条正常包完好**，才真正证明超长包没留残渣）、短包被拒、**头里撒谎**（声明长度与实际包长不符）被拒、对端关闭；④ `recv_timeout` 的到期与命中两条路径；⑤ 接听点路径四情形（0660 落实、非 socket 拒绝**且不删文件**、残留 socket 重建、父目录缺失、路径过长）；⑥ 白名单纯逻辑 + 真实 `accept` 鉴权（规则命中但 uid 不在名单 → `IV_EAUTH`）。

### S8 配置模块

**一句话**：给 `ivsboxd` 做一个**配置管家** —— 运行参数（连哪个平台、用哪个网口、探活多久算超时……）存在 `/mnt/UDISK/ivsbox/config/*.json` 里，程序**能读出来用、能改回去存、改坏了不会把服务搞崩、改了文件不用重启就生效**。

#### 本步要实现的八个功能

| # | 功能 | 外部可见的行为 |
|---|---|---|
| **F1** | **读配置** | 启动时从 `/mnt/UDISK/ivsbox/config/<名>.json` 读出全部参数到内存 |
| **F2** | **按名取参数** | 别的模块用 `net.wan.mode` 这种键取值，分字符串 / 整数 / 布尔三种类型；取一次之后就跟文件、跟 JSON 无关了 |
| **F3** | **改参数并保存** | 程序自己能把参数改掉写回文件；保存前先整体校验，不合法就**一个字段都不写**、文件保持原样 |
| **F4** | **缺就补默认** | 文件不存在、是空文件、或少了某个字段 ⇒ 用**内置默认值**补上，**照常启动**；只有"值非法"才拒绝 |
| **F5** | **抗断电写盘** | 写盘过程中断电，重启后文件要么是完整的旧配置、要么是完整的新配置，**绝不会是半截文件** |
| **F6** | **热更新** | 外部改了配置文件（手工编辑 / Web 下发 / OTA 恢复），程序**不重启**就能发现并生效；新配置里有非法值 ⇒ **保留旧配置继续跑** + 日志告警，不因为一次坏配置就停服 |
| **F7** | **事务通知** | 配置生效后通知依赖它的模块；**要么全生效、要么全不生效**，不允许一半新一半旧 |
| **F8** | **密钥分离** | 口令 / 令牌不写在普通配置里，放 `secure/` 目录（`0600`）；普通配置里只写"去哪儿取" |

> 另有一条不算功能但必须有：每份配置带**内容版本号**，Web 提交配置时带上"我基于哪个版本改的"，版本不符就拒绝 —— 防止两个人同时改、后写的把先写的覆盖掉（给 M5 的 S5.4 用）。

| 2 | F4 + 校验：内置默认值表、缺值补齐、非法值拒绝 | 删掉任意键/整份文件都能照常启动；非法值被明确拒绝并指出键名 |
| 3 | F3 + F5：改值、整体校验后才落盘、抗断电原子写 | 非法改动一个字段都不落盘；断电模拟（只留 tmp）后重读仍是旧值 |

#### 实现时必读的三个坑

1. **json-c 跨版本**：宿主头是 0.15、板端 sysroot 是 0.13.1 ⇒ **只准用两边都有的 API**。2026-09-29 已实测两端都能编译链接的一批：`json_object_new_object` / `json_object_object_add` / `json_object_new_string` / `json_object_new_int` / `json_object_object_get_ex` / `json_object_get_string` / `json_object_to_json_string` / `json_tokener_new` / `json_tokener_parse_ex` / `json_tokener_get_error` / `json_object_put` / `json_tokener_free`；**禁用** `json_object_new_uint64` / `json_object_get_uint64` 这类 0.15 才新增的接口。
2. **热更新必须 watch 目录、不能 watch 文件**：原子写走 `rename`（新文件替换旧文件），对**旧 inode** 的 watch 会立刻失效。要监听目录的 `IN_CLOSE_WRITE | IN_MOVED_TO`，再按文件名过滤。
3. **`rename` 之后必须 `fsync` 目录**：否则改名本身可能还没落盘，断电后可能出现"旧文件还在"。只 `fsync` 文件不够。

### S2.1 hal/serial 串口

- **实现什么**：`termios` raw 模式串口，纳入 Reactor。

- **实现什么**：对字节流的成帧：半包、粘包、噪声重同步、长度上限、校验失败、帧超时。

### S2.3 UART 可靠层

- **实现什么**：兼容现有采集板协议的命令级可靠收发。
- **怎么实现**（`src/modules/link/iv_link.c`）：协议有请求号+ACK → 直接做超时重传＋去重表；没有 → 命令级确认＋状态回读；**门锁/电源类控制幂等或带事务号**（防重传重复动作）；链路恢复后发全量状态同步请求重建镜像（对接 S2.6）。
- **怎么验证**：与 `uart_simulator`（S2.7）对联：正常收发、丢 ACK 触发重传、重复帧被去重、断链重连后镜像同步；真实采集板可用时冒烟。

### S2.4 平台协议

- **实现什么**：与云平台的私有协议栈：连接、表驱动命令路由、分级发送队列、断线补传。
- **怎么实现**（`src/modules/proto/`）：
  1. 连接管理挂 Reactor：非阻塞 connect、断线退避重连（1s→2s→…→60s 封顶）。
  2. 命令路由表：`{cmd, mode(本地/转发采集板/本地并转发), handler}`；未知命令按白名单决定是否透传（禁无条件透传）。
  3. 发送队列四级：门禁/控制 > 告警 > 状态 > 媒体；每级字节＋条目上限，满则丢最低优先级并计数。
  4. 每请求带关联号、超时、幂等键。
- **怎么验证**：`platform_simulator`（S2.7）对联：注册/心跳/上行告警/下行控制（含转发采集板路径）/未知命令按白名单处置/断线重连；VM 上 `tc netem loss 20%` 验证超时重传与队列降级。

### S2.5 GPS 与时间

- **怎么实现**（`src/modules/gps/`）：板上有 `gpsd` 则读其 socket；否则最小 NMEA 解析器（`GGA/RMC` 子集，其他语句直接跳过）；首次有效定位立即上报，此后按位移阈值或最长周期；时间源优先级平台/GPS/NTP/RTC 可配，小偏差渐进调（`adjtime`），大偏差审计后 `settimeofday`。
- **怎么验证**：host 用录制的 NMEA 样本回放单测（有效/无效/半句/乱序）；板上接 GPS 模组（或串口灌样本）看上报报文与 `date` 跳变日志。

### S2.6 状态镜像

### S5.1 ivsbox-web 服务

- **实现什么**：独立 Web 进程：静态页＋REST＋受控代理，无特权运行。
- **怎么实现**（`web/`）：选型固定一种成熟嵌入式 HTTP 库或 uhttpd（登记选型并固化版本）；监听端口可配；上限：连接数、请求体大小、上传大小、代理响应大小、各类超时；数据一律走本地通道（M1-S7）请求 `ivsboxd`/`ivsbox-media`，不直接开数据库、不写配置文件；init 脚本 ＋ `monitor.sh` 循环守护、独立非特权用户。
- **怎么验证**：`ab -n 10000 -c 50` 压测无 fd 泄漏（`ls /proc/<pid>/fd | wc -l` 稳定）；超限请求被拒返回稳定错误码；kill 后守护循环拉起且 `ivsboxd` 不受影响。

### S5.2 REST API

- **实现什么**：§9.1 八页面对应的全部 API。
- **怎么实现**：`GET` 查询、`POST` 建任务（长任务返回 task_id）；全部写操作鉴权＋审计（经本地通道落 `control.db`）；高风险操作（开锁/电源重启/升级/身份写入/代理授权）二次确认；错误码表独立文档化；**禁止** API 拼接 shell。
- **怎么验证**：curl 全接口回归脚本（正常/未登录/越权/超长输入）；重放拦截（nonce/时间窗）；审计记录逐条核对。对照 §16.1 安全测试"鉴权绕过、重放、SSRF"。

### S5.3 八个页面

- **实现什么**：总览/网络/摄像机/设备档案/交换机/媒体/配置/运维。
- **怎么实现**：静态资源 `web/static/`，纯 HTML+JS+轮询或 SSE（无重框架）；配置页走 S5.4 事务接口；媒体页在 M6 前显示"未启用"占位。
- **怎么验证**：浏览器逐页走查（数据来自本地通道快照）；配置页提交非法值被前端与后端双重拦截。

### S5.4 配置事务与热更新（Web 路径）

- **实现什么**：Web 改配置的完整链路：提交→校验→原子写→事务通知→生效确认。
- **怎么实现**：复用 M1-S8 配置模块；Web 只发本地通道 `config.apply`（带版本号防覆盖更新，ETag 语义）；失败保留旧配置并回显明确错误。
- **怎么验证**：改探活参数→模块日志确认热生效且无部分生效；并发双写冲突被版本号拦截。

### S5.5 ivsbox-provision 出厂工装

- **实现什么**：设备 ID/MAC 写入工具，量产口径。
- **怎么实现**（`tools/provision/`）：独立可执行，仅工厂模式可运行（`/mnt/UDISK/ivsbox/factory/enable_provision` 标记存在时）。**身份落点改到 eMMC `private` 裸分区**（`/dev/by-name/private` = `/dev/mmcblk0p8`，16 MiB，实测全 0、未格式化、未挂载）：定长二进制记录（设备 ID / MAC / 型号 / 硬件版本 / 出厂时间 ＋ CRC32），**直接 `open` + `write` + `fsync` 写裸设备、不建文件系统**；写入后置锁定位（`flags.locked`）⇒ 此后一律只读，二次写入被拒。`enable_provision` 标记本身是普通文件，放 UDISK 命名空间内；量产后删除该标记即关闭入口；不进日常自启。
- **怎么验证**：工装流程演练——写入→重启→`iv_version`/平台上报携带新身份；二次写入被拒；删除标记后运行直接退出。

**M5 退出条件**：权限与审计测试通过；S5.2 回归脚本全绿。

## M6 媒体与音频

前置：§18.5（录像路数/码率/SD 容量/保留周期）；S6.6 另需 §18.6（音频硬件与广播需求）。

### S6.1 ivsbox-media 骨架

- **实现什么**：媒体进程：本地通道服务端＋有界任务队列＋资源限额。
- **怎么实现**（`media/src/`）：控制循环处理本地通道请求（`record.start/stop`、`snapshot.take`、`media.list`、`audio.play/stop`）；每路 RTSP 会话独立 pipeline，数量受 `media.max_channels`；崩溃只重启自身（由 `monitor.sh` 循环拉起），`ivsboxd` 侧通道心跳检测"存在但不响应"并主动要求重启。
- **怎么验证**：通道心跳丢失→`ivsboxd` 请求守护循环重启 media（日志证据）；media kill -9 循环 20 次主控业务不中断。

### S6.2 抓图

- **实现什么**：门事件/平台/Web 三来源的抓图落盘与上报。
- **怎么实现**：优先摄像机 HTTP 抓拍接口（海康 ISAPI/大华 CGI 适配层），失败退 RTSP 关键帧；多路默认串行或低并发（配置）；临时文件 `fsync`＋`rename` 原子落盘→`media.db` 索引→通道完成事件→`ivsboxd` 上报；缩略图生成（选型登记）。
- **怎么验证**：开门事件触发抓图全链路时延与成功率（实验室 20 次）；抓图失败仅告警不影响门事件上报（§16.2 场景 4 后半）；断电瞬间的 tmp 文件不进索引。

### S6.3 断网录像

- **实现什么**：主网＋平台双确认后的本地 RTSP 录像。
- **怎么实现**：触发条件＝S3.2 探活判定主网与平台均不可用且保持配置时长；恢复后延迟停止防抖动；**码流直封装不转码**（FFmpeg libavformat remux）；1~5 分钟切片，关闭成功后 `rename`；每会话建连/无数据/读写/停止四类超时；总路数、总码率、写盘带宽上限。
- **怎么验证**：断网场景录制→恢复→文件可被 VLC/ffprobe 正常解析且时间连续；拔 SD 卡录制中→进程不崩、恢复挂载后继续；§16.2 场景 5。

### S6.4 视频读取（上传/下载）

- **实现什么**：录像文件的远程读取通道。
- **怎么实现**：方式一：设备主动向平台文件服务分片上传（4G 私网主路径，限速可配）；方式二：HTTP Range 下载（供 Web/授权通道，支持 Range/ETag/校验值/限速/取消）；**与大文件传输和控制在传输层隔离**，不与控制指令共队列。
- **怎么验证**：上传中断续传序号正确；Range 请求 206 与全量 sha256 一致；限速生效（`iftop` 观测不影响并行的平台心跳）。

### S6.5 SD 卡策略

- **实现什么**：存储水位、清理、异常检测。
- **怎么实现**：定时巡检挂载/只读/IO 错误/剩余空间（`statfs`）；水位线：85% 清理最旧可删→90% 拒新任务→95% 停录告警→70% 恢复；三类保留优先级（抓图>告警录像>普通录像）；按切片关闭同步而非每包 `fsync`。
- **怎么验证**：灌数据到水位线触发各级动作（日志＋行为）；满盘/只读/拔卡注入时控制业务不受影响（§16.2 场景 6）。

### S6.6 音频广播（前置：§18.6 确认）

- **实现什么**：`audio_sink` 统一接口与优先级播放。
- **怎么实现**：sink 实现：ALSA/I2S 本地、网络音柱、摄像机语音对讲、采集板预置资源（按 §18.6 结论裁剪）；任务字段：编码/音量/优先级/有效期/目标；紧急>告警>通知可抢占；实时流配抖动缓冲与无数据超时。
- **怎么验证**：按确认后的硬件形态定（本地功放放音、抢占时延、断流超时停止）。

**M6 退出条件**：资源上限与异常恢复通过（§16.2 场景 5/6）。

## M7 OTA 与加固

前置：§18.7（OTA 范围：应用/采集板固件/系统镜像）。

### S7.1 升级包格式与验签

- **实现什么**：带强制签名的升级包格式与验签器。
- **怎么实现**：包内清单：产品型号、硬件版本范围、软件版本、最低可回滚版本、文件清单、SHA-256、数字签名（mbedTLS/OpenSSL，Ed25519/ECDSA）；设备内置只读公钥；`ivsboxd` 只协调（收命令/下载/上报进度），验签安装归 `ivsbox-updater`。
- **怎么验证**：正常包通过；篡改单字节被拒；型号不匹配被拒；无签名被拒（§16.2 场景 9）。

### S7.2 ivsbox-updater 与双版本切换

- **实现什么**：root 按需运行的安装器，应用级 A/B。
- **怎么实现**（`updater/`）：目录 `/mnt/UDISK/ivsbox/releases/<ver>/`、`current`/`previous` 符号链接；流程：下载到临时目录→验签→解压新版目录（查权限/架构/依赖）→临时符号链接 `rename` 原子切 `current`→写 `/mnt/UDISK/ivsbox/ota/pending.json`→重启业务；新版本健康自检（平台/UART/配置/DB/媒体通道）通过才确认，否则启动包装程序恢复 `previous`。
- **怎么验证**：正常升级路径全链路；升级中掉电→重启后旧版本可运行；新版自检失败→自动回滚（§16.2 场景 8 前半）。

### S7.3 回滚与启动包装

- **实现什么**：开机自检与自动回滚兜底。
- **怎么实现**：`current/bin/ivsboxd` 由包装脚本启动，记录 `bootcount`；连续 N 次启动失败或自检超时→切回 `previous` 并置告警；应用级回滚不用 U-Boot rootfs 槽位冒充（系统级 A/B 另立项，见架构 §11.3）。
- **怎么验证**：`bootcount` 超限注入→回滚；回滚后平台收到版本回退事件。

### S7.4 故障注入加固

- **实现什么**：§16.1 故障注入类目的全量通过。
- **怎么实现**：按清单执行——弱网、双网断开、串口拔出、SD 满/拔卡、进程卡死（SIGSTOP 各进程）、掉电（升级中/录像中/写库中）。
- **怎么验证**：每项注入后系统行为符合架构预期并留测试记录（§16.2 场景 7）。

### S7.5 长稳测试

- **实现什么**：≥72 小时连续运行。
- **怎么实现**：脚本化周期触发网络切换、媒体启停、通道查询；监测 RSS/fd/线程数/DB 大小斜率。
- **怎么验证**：72h 无重启、无 OOM、资源曲线平稳。

**M7 退出条件**：断电回滚正确＋72h 长稳通过＋§16.2 场景 7/8/9 通过。
