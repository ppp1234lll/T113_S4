## 0. 一句话

**Windows 写代码 → ssh 进编译 VM 编译 → VM 内 scp 推给开发板 → Windows COM4 串口看结果。**
Windows 本机不做编译（没有 cmake/make/clang），只负责编辑、git 主副本和串口控制台。

```text
+---------------------------+

|  f:\debug\T113_TCP        |
|  - 代码编辑 / git 主副本    |
|  - COM4 串口控制台(115200)  |
+---------------------------+
        |                    \

        v                      v
+---------------------------+   +----------------------------+
|  编译 VM  tqt113           |   |  开发板 TQT113             |
|  192.168.2.115 / embedsky |   |  192.168.2.105 / root      |
|  - 主机侧单测 build/host    |scp| - 运行 /tmp/ivsboxd        |
|  - ARM 交叉编译 build/arm  |-->| - logread / 设备节点        |
|  工具链 /opt/EmbedSky/Tina |   |  Buildroot + glibc 2.25    |
+---------------------------+   +----------------------------+
```

| 角色 | 地址 / 位置 | 干什么 | 不干什么 |
|---|---|---|---|
| Windows 本机 | `f:\debug\T113_TCP` | 编辑代码、git 主副本、COM4 串口 | **不编译**（无 cmake/make/clang）、不直连板子 |
| 编译 VM | `ssh tqt113` = 192.168.2.115，用户 `embedsky` | 主机侧单测（`build/host`）+ ARM 交叉编译（`build/arm`） | 不长期放源码副本（每次 `git pull` 对齐） |
| 开发板 | 192.168.2.105，用户 `root` | 跑二进制、看日志、验设备节点 | 不在板上编译（无 gcc） |

**为什么这么分工（不是随手定的）**

- 本机 Windows **无 cmake / make / clang / ninja**，ARM 交叉编译只能在 VM 做。
- 交叉工具链在天嵌 VM 的 `/opt/EmbedSky/Tina`，且**已在 PATH 内**，VM 里不需要额外配 PATH 或指绝对路径。
- VM 与开发板同在 `192.168.2.0/24`，所以 **scp 从 VM 发**最省事；Windows 不必装 scp 客户端、也不必能被板子路由到。
- 板子只有 220MB 内存、Buildroot 精简 rootfs（**无 gcc / 无 strace / 无 socat**），不适合当构建机。

**凭据口径**：本文所有口令一律用占位符（`AGENTS.md` 规则 3.6：密钥口令禁止入库）。实际口令见你本地记录；如需在命令里非交互传口令，见 §6.4。

## 4. 步骤 1：SSH 连接虚拟机

```sh
# 交互式登录（人工用）
ssh tqt113

# 或非交互跑一条命令（脚本/自动化用，走密钥免密）
ssh tqt113 "cd ~/work/T113_S4 && git log --oneline -1"
```

登录后**先对齐代码基线**（规则 7 第 6 条：开工前先同步）：

```sh
cd ~/work/T113_S4
git fetch origin
git checkout main
git pull --ff-only
git log --oneline -1        # 应与本机 main 的 HEAD 一致
git status -sb              # 期望干净
```

VM 侧需知：

- **第一次连**会问主机指纹，输 `yes` 即可；之后进 `~/.ssh/known_hosts`。
- **`sudo` 需要密码**（实测非免密），会话内多次 sudo 有缓存。
- 源码进 VM 的正规途径是 git（`git clone/pull`）；只有临时改一两个文件才用 scp 传。

## 5. 步骤 2：在虚拟机中编译

### 5.1 先跑主机侧单测（`build/host`）——先绿再上板

```sh
cd ~/work/T113_S4
cmake -S ivsbox-v5 -B ivsbox-v5/build/host -DIVSBOX_BUILD_TESTS=ON
cmake --build ivsbox-v5/build/host -j
ctest --test-dir ivsbox-v5/build/host --output-on-failure
```

- 主机侧可跑单测，是因为 `ivcore`（事件/队列/日志/配置/CRC）**不允许依赖 Linux HAL**，能在开发机跑。
- `ctest` 必须全绿再进 5.2。**上板一次的代价远大于本地重编一次。**

### 5.2 再交叉编译 ARM（`build/arm`）

```sh
cd ~/work/T113_S4
cmake -S ivsbox-v5 -B ivsbox-v5/build/arm \
  -DCMAKE_TOOLCHAIN_FILE=$PWD/ivsbox-v5/cmake/toolchains/tina-arm.cmake \
  -DIVSBOX_BUILD_TESTS=OFF \
  -DCMAKE_BUILD_TYPE=Release

cmake --build ivsbox-v5/build/arm -j

# 校验产物架构（这一步不能省）
file ivsbox-v5/build/arm/ivsboxd
```

期望：`ELF 32-bit LSB executable, ARM, EABI5 ...`

- 打出 `x86-64` → `-DCMAKE_TOOLCHAIN_FILE=` 没生效（路径写错 / 相对路径 `$PWD` 不对）。
- 工具链文件已把 `IVSBOX_BUILD_TESTS` 强制 OFF，显式传 `-DIVSBOX_BUILD_TESTS=OFF` 只是写明意图。
- `-DIVSBOX_LOG_SYSLOG=ON` 是 **S02 步骤 4 之后**才存在的 CMake 开关（见 `操作手册/S02-core基础设施操作手册.md` §4）。**S02 未实现前传它只会让 CMake 打一条 "Manually-specified variables were not used" 告警，不报错也不生效。**

### 5.3 编译期铁律

- `build/` **必须落在 VM 本地盘**（如 `~/work/`），**不要放 Windows 共享目录**：`fsync` 与并发 IO 会变慢并偶发异常。
- 工程默认 `-Wall -Wextra ... -Werror`（`IVSBOX_WERROR=ON`）。告警即失败，别用 `-DIVSBOX_WERROR=OFF` 绕，按提示改代码。
- 想重新来一遍：删掉对应 `build/<target>` 目录再跑 cmake，或 `cmake --build <dir> --target clean`。
- 只看某个目标：`cmake --build ivsbox-v5/build/arm --target ivsboxd -j`。

## 6. 步骤 3：SCP 推送文件到开发板

**在 VM 内执行**（VM 与板子同网段；Windows 不做这一步）。

### 6.1 推二进制上板

```sh
# VM 内
cd ~/work/T113_S4
scp ivsbox-v5/build/arm/ivsboxd root@192.168.2.105:/tmp/ivsboxd
```

- 目标目录用 **`/tmp`**：板子 root 分区余量有限，反复写 flash 没必要；`/tmp` 掉电即失，正好当暂存。正式安装路径（`/opt` 等）到 S20 打包再定。
- 板子 rootfs 有 `scp`/`ssh`（`dropbear`/`openssh` 客户端侧已确认存在），所以**也能反过来从板子拉文件**：

```sh
# 板端产物回传到 VM（例：盘点输出、日志、抓图）
ssh  root@192.168.2.105 "/tmp/xxx.sh > /tmp/out.txt 2>&1"
scp  root@192.168.2.105:/tmp/out.txt ~/work/
# 再从 VM 拉回 Windows（在 Windows 侧执行）
# scp tqt113:~/work/out.txt f:\debug\T113_TCP\
```

### 6.2 校验传没传对（大文件/网络不稳时必做）

```sh
# VM 侧
md5sum ivsbox-v5/build/arm/ivsboxd
ssh root@192.168.2.105 "ls -l /tmp/ivsboxd; md5sum /tmp/ivsboxd"
```

板端是 busybox，`md5sum` 属常规 applet；若该 applet 未编入，退回 **比字节数**（`ls -l` 两边大小一致即视为传完）。

### 6.3 传源码（临时改文件，非正规途径）

```sh
# 只推改动的文件，别整目录盖
scp ivsbox-v5/src/core/iv_config.c root@192.168.2.105:/tmp/src/
```

> 注意：板子上**没有 gcc**，传 `.c` 过去不能编译；这条路径只用于传脚本、配置、shell 工具（如 `scripts/bsp-survey.sh`）。

### 6.4 口令相关（2026-09-24 实测更新）

- **好消息：VM → 板子的密钥免密已经配好了。** 实测
  `ssh -o BatchMode=yes root@192.168.2.105 "echo ok"` 直接返回成功，
  `scp` 全程不需要任何口令（VM 公钥 `~/.ssh/id_ed25519.pub` 已在板端 `authorized_keys` 内）。
  所以 §6/§7 的命令可以直接非交互执行、可脚本化，**不必手工输密码**。
- VM 上**没有装 `sshpass`**（实测 `command -v sshpass` 为空）；免密已通，不必再装。
- **免密失效时怎么恢复**（重刷 rootfs / 换板子 / 换 VM 才会遇到）：在 VM 内
  `ssh-keygen -t ed25519`（若还没有）+ `ssh-copy-id root@192.168.2.105`，之后恢复免密。
- 交互式 `ssh`/`scp` 需要口令时直接输即可；**不要把口令写进脚本或文档**（规则 3.6）。
- 板子如果改过 root 口令且与文档记录不一致，**以板端实际为准**，并回写本文 §3 与 `bsp-capability.md`。

### 6.5 板端 console 的当前状态

实测（2026-09-24）板端串口 console **已处于 root 登录态**，提示符为 `root@TQ113:/tmp #`，
所以通过 COM4 下发命令**不需要再发用户名/口令**。若某次上电后停在 `login:`，才按 §7.4 补发。

## 7. 步骤 4：COM4 串口连接开发板通信

### 7.1 前置：确认端口与"独占"

```powershell
# 列出本机串口
[System.IO.Ports.SerialPort]::GetPortNames()
```

**串口在 Windows 上是独占的**：SecureCRT / MobaXterm / PuTTY 开着占用了 COM4，脚本 open 就会报
`PermissionError` / `Access is denied`。**必须先关掉终端软件**再跑脚本。

### 7.2 方式 A（推荐）：脚本化批量下发 + 抓输出

把要执行的命令**一行一条**写进 `cmds.txt`，然后：

```powershell
$py = "C:\Users\Think\.workbuddy\binaries\python\envs\default\Scripts\python.exe"
$sk = "C:\Users\Think\.workbuddy\skills\serial-console-debug\scripts"
$wd = "<本次调试工作目录>"

# 下发并落盘
& $py "$sk\serial_run.py" COM4 115200 "$wd\cmds.txt" "$wd\serial_out.txt" *>&1 |
    Out-File "$wd\_run.log" -Encoding utf8

# 洗掉 ANSI/控制字符（不洗的话输出会被当成二进制，读不了）
& $py "$sk\sanitize.py" "$wd\serial_out.txt" "$wd\serial_out_clean.txt" *>&1 |
    Out-File "$wd\_san.log" -Encoding utf8
```

然后读 `serial_out_clean.txt`。

> `$sk` 来自用户级 skill `serial-console-debug`（本机路径见上）；skill 升级或换机时路径会变，
> 用 `serial_run.py` / `sanitize.py` 这两个**脚本名**去找即可。
> （`操作手册/S02-core基础设施操作手册.md` §7 里写的 `serial_send.py` 是笔误，实际脚本名为 `serial_run.py`。）

### 7.3 方式 B：人工交互终端

```powershell
plink -serial COM4 -sercfg 115200,8,n,1,N
# 需要留日志时：
plink -serial COM4 -sercfg 115200,8,n,1,N -sessionlog serial_term.log
```

`plink` 在本机 `C:\Program Files\PuTTY\plink.exe`。

### 7.4 板端登录

板端 console 有登录提示时，脚本方式把用户名、密码**各占一行**写进 `cmds.txt`：

```text
root
<板子 root 密码>
```

### 7.5 串口通信铁律（踩过的坑）

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 命令之间不留时间 | 命令还没执行完就发下一条，输出错位 | 每条之间留 **4~5s** 采集时间 |
| 长输出直接打 | `dmesg`/`ls -R` 溢出，抓不全还卡 | 板端就用 `\| head -n 50` 截断 |
| 只发 `\n` | 有的嵌入式 shell 不认 | 发 `\r`（CR）即可，或 `\r\n` |
| 输出直接 Read | ANSI 转义导致"binary file"拒读 | 先过 `sanitize.py` |
| 日志里打中文 | 板端控制台 GBK，乱码没法看 | **程序输出的日志文本一律 ASCII**，中文只进注释 |
| 边用终端边抓包 | 口被独占，抓不到 | 二选一；要边操作边抓就走旁路监听（另备一根 USB-TTL，RX 接板子 TX、GND 共地、TX 悬空） |

### 7.6 板端联网时更省事的做法

板子能上网就 **操作走 ssh、串口专职做日志口**（脚本可 7x24 独占 COM4 抓日志），不要用串口敲命令。

```sh
# 2. 开隔离会话（规则 8）——见 §9

# ---- 编码 ----
# 3. 在 worktree 内改代码 / 文档

# ---- 编译 VM ----
# 4. 代码进 VM：正规途径 git（push 会话分支后 VM fetch），临时改动可 scp
ssh tqt113

# 5. 单测先绿

# 6. 交叉编译 + 校验架构

cmake --build ivsbox-v5/build/arm -j && file ivsbox-v5/build/arm/ivsboxd

# 7. 推上板
scp ivsbox-v5/build/arm/ivsboxd root@192.168.2.105:/tmp/ivsboxd

# ---- Windows 本机 COM4 ----
# 8. cmds.txt 内容（示例）：
#     chmod +x /tmp/ivsboxd
#     /tmp/ivsboxd ; echo RUN_EXIT=$?
#     logread | grep -i ivsbox
#     ls -l /opt/ivsbox/config/
#    然后用 §7.2 的两条命令下发 + 洗字符 + 读 serial_out_clean.txt

# ---- 收尾 ----
# 9. 清理临时物（规则 6）：板端残留、VM 侧一次性脚本、本机 _*.txt / *.log
# 10. 回写文档（规则 1/2/4）→ 提交推送（规则 3）
```

**看结果的三条常规判据**

1. 进程本身：`/tmp/ivsboxd ; echo RUN_EXIT=$?` → 期望 `RUN_EXIT=0` 且版本行正常。
2. 日志：`logread | grep -i ivsbox` → S02 之后日志走 syslogd，期望能看到 `ivsboxd` 的 INFO/WARN 行。
3. 产物/副作用：如 `ls -l /opt/ivsbox/config/`、`cat /opt/ivsbox/config/ivsbox.conf`。

冒烟完成后**清理板端残留**（例：`rm -rf /opt/ivsbox`，避免与后续联调的旧文件混淆）；`/tmp/ivsboxd` 可留。

### 8.1 环境自检：hello world 端到端实测（2026-09-24，已通过）

**什么时候用**：第一次拿到板子、换过 VM、换过工具链、或怀疑链路某一段坏了。比直接编 `ivsboxd` 更快定位问题出在哪一段。
**本轮结论**：四段链路全部打通，工具链与板端 glibc 版本严格匹配。

**① 自检程序 `hello.c`**（一次性测试程序，验证完即清理，按规则 6 不入库；下方源码可原样复现）

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdint.h>
#include <time.h>
#include <gnu/libc-version.h>

static int is_little_endian(void)
{
    union { uint16_t u; uint8_t b[2]; } probe;
    probe.u = 1u;
    return probe.b[0] == 1;
}

int main(void)
{
    struct timespec ts;

    printf("Hello, IVSBox!\n");
    printf("ptr_bits=%u\n", (unsigned)(sizeof(void *) * 8u));
    printf("little_endian=%d\n", is_little_endian());
#if defined(__ARM_EABI__) || defined(__arm__)
    printf("target_arch=arm-eabi\n");
#elif defined(__x86_64__)
    printf("target_arch=x86_64\n");
#else
    printf("target_arch=unknown\n");
#endif
    printf("compiler=%s\n", __VERSION__);
    printf("glibc=%s\n", gnu_get_libc_version());
    if (clock_gettime(CLOCK_MONOTONIC, &ts) == 0)
        printf("mono_ms=%lld\n",
               (long long)ts.tv_sec * 1000LL + (long long)(ts.tv_nsec / 1000000L));
    else
        printf("mono_ms=ERR\n");
    printf("hello_exit=0\n");
    return 0;
}
```

**② 四段命令**

```sh
# 段1 Windows → VM
scp hello.c tqt113:/tmp/envcheck/hello.c

# 段2 VM 内：主机编译 + ARM 交叉编译
cd /tmp/envcheck
SYSROOT=$(arm-linux-gnueabi-gcc -print-sysroot)   # = /opt/EmbedSky/Tina/arm-buildroot-linux-gnueabi/sysroot
gcc -std=c11 -Wall -Wextra -O2 hello.c -o hello_host && ./hello_host
arm-linux-gnueabi-gcc -std=c11 -Wall -Wextra -O2 --sysroot=$SYSROOT hello.c -o hello_arm
file hello_arm

# 段3 VM → 板子
scp hello_arm root@192.168.2.105:/tmp/hello_arm

# 段4 Windows COM4：cmds.txt 写三行，再用 §7.2 的 serial_run.py + sanitize.py
#   /tmp/hello_arm
#   echo RUN_EXIT=$?
#   uname -m
```

**③ 实测输出（2026-09-24 09:35，原文摘录）**

| 环节 | 输出 |
|---|---|
| VM 主机运行 | `Hello, IVSBox!` / `ptr_bits=64` / `target_arch=x86_64` / `compiler=11.4.0` / `glibc=2.35` / `HOST_EXIT=0` |
| ARM 产物 | `ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux.so.3, for GNU/Linux 3.2.0`；`NEEDED: libc.so.6` |
| 板上运行 | `ptr_bits=32` / `target_arch=arm-eabi` / `compiler=7.3.1 20180425 [linaro-7.3-2018.05 ...]` / **`glibc=2.25`** / `mono_ms=1789774` / `hello_exit=0` / `RUN_EXIT=0` |
| 板端架构 | `uname -m` → `armv7l` |
| 传输校验 | `hello.c` 两侧 md5 一致（`b5079d27…`）；`hello_arm` 两侧 md5 一致（`2266f6f1…`） |
| 动态链接器 | 板端 `/lib/ld-linux.so.3 -> ld-2.25.so`，与交叉 sysroot 的 **glibc 2.25 完全一致** |

**④ 这次自检证明了什么**

1. VM 的 cmake / 交叉工具链 / SSH 免密都正常，主机侧与交叉两套编译都能出产物。
2. **板端 glibc 2.25 == sysroot glibc 2.25** → 交叉产物可直接在板上跑，不存在 glibc 版本坑。
3. `CLOCK_MONOTONIC` 在板上可用（`mono_ms` 有值），S02 的单调时钟纪律有硬件基础。
4. COM4 既能只读抓取也能批量下发；控制台是 root 登录态（`root@TQ113:/tmp #`），无需口令。
5. 板端是 busybox，`ldd --version` **不可用**（无输出）——判断 glibc 版本要看 `/lib/ld-*.so` 指向，别指望 `ldd`。

**⑤ 自检后的清理（规则 6）**：`rm -f /tmp/hello_arm`（板端）、`rm -rf /tmp/envcheck`（VM）、删除本机临时工作目录。自检程序本身不放仓库。

## 9. 会话隔离（规则 8）——本机现状

**规定动作**（TRAE 用 `trae-<主题>`，WorkBuddy 用 `wb-<主题>`）：

```powershell
git fetch origin
git status -sb                                   # 必须干净且与 origin/main 一致
git stint start wb-<主题>
cd .stint/wb-<主题>/                              # 所有改动只在这个 worktree 内
git stint track <文件...> --session wb-<主题>     # 不 track，conflicts 检测不到重叠
git stint conflicts --session wb-<主题>
# 收尾
git stint commit -m "<Conventional Commits>" --session wb-<主题>
git stint squash -m "<最终提交信息>" --session wb-<主题>
git fetch origin ; git stint merge --session wb-<主题>
git push
git stint list                                   # 期望 No active sessions
```

**本机已知问题（2026-09-24 实测）**：`git stint list|start` 报
`Error: git rev-parse failed: spawnSync git EBUSY` / `Error: Not inside a git repository`，
而同一目录下 `git status` 正常——是 git-stint 自身 spawn git 失败，**加不加沙箱都一样**。

**等价的降级方案**（仍是物理隔离，不违反"禁止在 main 工作副本直接改文件"）：

```sh
git worktree add .stint/wb-<主题> -b stint/wb-<主题>   # .stint/ 已被 .gitignore 忽略
cd .stint/wb-<主题>/                                   # 改动只在这里
# 收尾：commit → 回 main 合并 → 清理
git -C .stint/wb-<主题> add <只加本次文件>            # 禁用 git add -A / git add .
git -C .stint/wb-<主题> commit -m "<Conventional Commits>"
git merge stint/wb-<主题>                             # 在 main 工作副本执行
git worktree remove .stint/wb-<主题>
git branch -d stint/wb-<主题>
```

无论哪种方式，**共用文档冲突（`AGENTS.md` / `修改记录.md` / `代码说明.md`）的处理原则都是"双方记录都保留、按时间倒序"**，绝不丢弃对方条目。

## 10. 常见故障速查

| 现象 | 大概率原因 | 处理 |
|---|---|---|
| `ssh tqt113` 超时 | VM 没开机 / 不在同一网段 / IP 变了 | 先在 Windows ping 192.168.2.115；IP 变了改 `~/.ssh/config` |
| `ssh` 报 `Host key verification failed` | VM 重装或 IP 复用，指纹变了 | 删掉 `known_hosts` 里的旧条目重连 |
| `cmake: command not found`（VM 内） | shell 命令哈希未刷新 | `hash -r` 或重开终端；仍无则按环境搭建文档装 |
| `file` 显示 `x86-64` | 工具链文件没生效 | 检查 `-DCMAKE_TOOLCHAIN_FILE=`；确认 VM 的 `command -v arm-linux-gnueabi-gcc` |
| 编译报隐式声明（`fsync`/`rename`） | 新文件没进对的 target，或没吃到 `_GNU_SOURCE` | 检查 `CMakeLists.txt` 里该文件所属 target；`UNIX` 目标已统一开 `_GNU_SOURCE` |
| `scp` 报 `Permission denied` | 板端口令不对 / 板子未开 sshd | 用 §6.4 的口径确认口令；板端 `ps \| grep -i ssh` |
| `scp` 卡住不动 | 网络不通或板子 IP 变了 | VM 内 `ping 192.168.2.105`；板端 `ip addr` 核对 |
| 板端 `Permission denied` 执行不了 | 没加可执行位 / 文件系统 noexec | `chmod +x /tmp/ivsboxd`；换到可执行目录跑 |
| 板端运行报 `not found`（明明文件在） | 动态库缺失或解释器路径不对 | `file` / `readelf -l` 看 interpreter；比对本机 `ld-2.25.so` 与 VM sysroot |
| 串口脚本报 `PermissionError` | COM4 被终端软件占用 | 关掉 SecureCRT/MobaXterm/PuTTY 再跑（§7.1） |
| 读串口输出是乱码 | 波特率/线序不对，或没洗字符 | 确认 115200；`sanitize.py` 洗一遍；检查 TX/RX 是否交叉 |
| 串口有回显但不执行命令 | 停在登录提示 / 需要 CR | 先发 `root` + 口令；发 `\r` |
| `git fetch/push` 失败 | 本机走 `127.0.0.1` 代理且代理没起 | `git config --get http.proxy`；起代理或临时 `git -c http.proxy= ...`（**失败必须如实上报，不得假装已推送**，规则 3.7） |
