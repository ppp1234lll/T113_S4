5. 缺陷清单与处理方案

R-01 · P1 · 清空平台地址后仍向旧地址上报

项内容
用例E-07「平台地址为空」
现象清空 net.server.wireless.host / wired.host 后 230 s 内 transport 恒 up，17:09:24 仍产生 report #6；ss -tn 显示 10.62.35.221:49780 → 47.104.250.225:6013 ESTAB
根因iv_report_set_server() 清空分支只清 srv_host/srv_port，注释明确"在用连接不动，是否断由调用方决定"；而 agent_reload_server()（iv_agent.c:1309）在 iv_agent_pick_host() 返回 NULL 时只调了 iv_report_set_server(rp, NULL, 0)，没有做"断"这个决定
影响运维想停上报（或换平台时先清空）时，设备会继续把状态数据发往旧地址，直到 TCP 自然断开（可长达数小时）。属数据外发不可控
方案① iv_report 增加 iv_report_disconnect()（复用重连路径里的 close）；② agent_reload_server() 在 h == NULL 时调用它，并把 transport 置 idle；③ 补一条单测：set_server(NULL,0) 后断言 fd < 0、state != up；④ 板端回归 E-07（清空后 200 s 内不得出现新 report）

R-02 · P1 · 摄像机探测结论错误（PORT 恒正常、PING 误判延时）

项内容
用例F-01「探测三方式」
现象ch0=192.168.2.102（PING 0.468 ms、可达）；ch1=192.168.2.199（100% 丢包、ARP 未解析）。
· PORT 模式：50 s × 10 次采样恒 cns=[1,1]，不可达的 ch1 报 NORMAL(1)；
· PING 模式：ch0 报 DELAY(4)（阈值 200 ms，实测 0.47 ms）；
· RTSP 模式：可达的 ch0 报 FAULT(2)
根因方向port_tick() 把结论写进 vd[]（sc_bits!=0 ? NORMAL : FAULT），CNS 读的是 st[]，两者由 refresh() 同步；实测 st 停在初值 1 ⇒ PORT 模式的轮次没有真正跑完 / 结论没有落进 vd，需加 port_tick 入口与 round_begin() 返回值的调试日志确认。PING 的 DELAY 需核 pk_rtt[] 记录的值与实际 0.47 ms 的对应关系（单位或首次 ARP 耗时被计入）
影响摄像机断线时平台仍看到"正常"（漏报故障，最坏情况运维完全失去监控意义）；PING 模式则相反，会把正常摄像机报成延时
方案① 先补一条 会失败的 单测：iv_camdet 配置一个不可达 IP，PORT 模式跑满一轮后断言 verdict==FAULT（现在 test_camdet 只覆盖 PING 与 §c13，故单测全绿而板端错）；② 修 port_tick 的状态回写；③ PING 侧用抓包/日志打印 pk_rtt[] 原值，检查阈值单位；④ 回归：三方式各跑 60 s，两路结论必须分别等于地面真值

R-03 · P2 · 超长字符串"报成功但没写入"

项内容
用例B-02（sys.device.name 200 字符）
现象应答 {"ok":true,"d":{"version":41,"applied":1}}，但回读值仍是原值（空串）——版本号前进、applied 计数 +1，实际没写
根因m_config_apply() 的②预检只校验"键存在 + 类型匹配"，不校验字符串长度；③写入阶段 iv_config_set_str() 因 strlen >= IV_CFG_STR_MAX(160) 返回 IV_ERANGE，而 apply_set() 的返回值被 (void) 丢弃；applied 用的是预检计数 n
影响所有 STR 键（设备名、平台地址、录像 URL 等）：填超长值时界面提示保存成功，实际未生效，属"配置骗人"
方案① 预检加一项：want==STR && strlen(json_get_string(v)) >= IV_CFG_STR_MAX → IV_ERANGE "value too long"；② apply_set() 返回 rc 并在非 IV_OK 时回滚整条；③ 单测：超长串必须 ok:false 且 version 不变

R-04 · P2 · device 表 IP 落库字节序反转

项内容
用例K-02「行数不变量」（顺带发现）
现象select ip from device 得 200.1.168.192、78.1.168.192、18.2.168.192、102.2.168.192；正确值应为 192.168.1.200 / .1.78 / 192.168.2.18 / 192.168.2.102。Web /api/devices 显示正确（走内存结构），仅 DB 错
根因方向ip 以 uint32 网络序存储，读回后按主机序 inet_ntop/手写格式化。项目已有同类教训（"_be 是原样字节序 ⇒ 打印用 inet_ntop()"）
影响任何按 DB 查询/导出/第三方对账拿到的摄像机 IP 全是错的；当前页面不读该列，故未被发现
方案① 统一"存 _be、读时 inet_ntop"，或直接存点分十进制字符串；② 加单测：写 192.168.1.200 读回必须逐字节相等；③ 修复后清一次历史错值（或加 schema 版本迁移）

R-05 · P3 · net.ip 无 IP 格式校验

net.ip="999.1.1.1" 保存成功。该键目前没有任何消费者（net.ip/mask/gateway 全仓只有默认表与注释，实际地址由系统/DHCP 决定），所以不影响运行；但 Web 上填垃圾值能保存，容易误导排障。 方案：给三个键加 IP 校验器，或在页面标注"仅记录，不改变系统地址"。

R-06 · P3 · 错误响应一律 HTTP 200

apply body=[]、cls=nosuch、login 畸形 JSON 均返回 HTTP 200 + {"ok":false,"e":…}（登录失败是 401）。前端按 ok 判断，功能正常，但与计划 G-09 的判据"稳定 4xx"不符。 方案：二选一——把判据改成"稳定返回 ok:false 且不崩"，或按 REST 惯例回 400/422；不要两边都不改，否则每轮都会"报红"。

R-07 · P3 · ui_camera_slot 用例桩缺 /api/snmp

摄像机页新增「查摄像机 SNMP」卡后，该用例的桩没补对应分支，默认桩返回 {ok:true,d:{}} ⇒ r.d.slots.length 抛 TypeError，用例整体中断（19 条断言全部未跑）。 方案：① 桩补 /api/snmp?which= 分支（照抄 ui_camera_test.mjs 的 slots 结构）；② 顺手把 app.js 的 r.d.slots.length 改成 (r.d.slots || []).length，避免后端异常响应把整页渲染打断。

R-08 · P0（待定位）· 一次非预期重启

项内容
现象17:15:20 最后一条日志（channel client connected）之后，17.log 出现 763 个 NUL 字节（掉电/硬复位特征，无 signal、无 shutting down）；17:15:42 重新启动，17:16:00 就绪；probe.log 里该时刻前 up=304 与重启后 boot_id 一致
